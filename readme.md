# 银行流水核对工具 v3.2

[![License: AGPL v3](https://img.shields.io/badge/License-AGPL_v3-blue.svg)](https://www.gnu.org/licenses/agpl-3.0)

这是一个面向审计项目的 Windows 桌面工具。每次核对接收一个银行账户的流水及其对应的银行存款序时账（旧界面和报告中也称“日记账”）。当前集中处理单账户的逐笔、合并拆分、批量收付款、退款退汇、冲销重付、手续费净额、重复线索和跨期关系，不做多文件合并、多账户批量或企业财务月度对账。程序自动生成对应关系、组级结论和疑点明细，不要求先填写人工结论才能出报告。

## 当前报告改版

报告现在默认只显示“核对概览、待复核事项、全部核对明细”。机器字段放入隐藏附表，问题按明确业务归并，双方记录可直接对照，筛选导出沿用同样结构。程序运行和人工复核分开：不填写人工意见也会生成完整报告。

详细使用方式见下文“Excel 报告”；本轮完整验证 552 项通过，真实桌面入口和实际 Excel 页面检查通过，详见[报告改版验收报告](docs/reviews/2026-09-06-报告阅读与复核改版-review.md)。需求、设计和实施计划保存在 docs 对应目录。程序入口不变，本轮更新源代码与文档，未重新打包旧 EXE。

## 此前业务能力升级：从反编译工具学了什么、重新做了什么

本次升级参考了用户提供的另一套银行流水核对程序及其说明文档，但没有复制其核心算法。**从对方工具吸收的主要是产品使用闭环；单账户审计核对规则、证据门槛、防误配机制和审计底稿结构，是结合实际审计需求及本项目原有能力重新设计的。**

### 没有照搬的算法及原因

反编译和场景复核发现，对方工具存在以下不适合审计直接采用的做法：

1. 宽松模式可能只凭账户和金额建立对应，日期、对方和摘要不一致也可能通过。
2. 重复金额可能按原表先后顺序占用，没有把真实多解作为疑点保留。
3. 同月汇总没有完整区分年份，存在跨年度同月合并风险。
4. 一借一贷或一正一负同额可能被误当成冲销，缺少共同业务证据。
5. 一对多搜索先截取部分大额记录、限制组合笔数并在首个结果处停止，可能漏掉正确完整组。
6. 金额或日期解析失败、空账户和界面参数传递存在失真风险。

因此，本工具没有复制其宽松确认、顺序抢占、错误冲销、静默解析和有限首解搜索。

### 按审计业务重新完成的核心提升

1. **单账户范围控制**：一次只核对一份银行流水和对应的一份银行存款序时账；检查账户、币种、期间、金额方向、原始人口和余额连续性。明确冲突时阻止错误确认，资料不能完整证明范围时降低结论等级。
2. **拆分合并和批量业务**：加强一对多、多对一、多对多、工资、奖金、报销、供应商批付、客户批收、税费和社保等业务；优先依据完整凭证、业务编号、批次号、日期、对方和摘要确定业务边界。批次缺项或存在差额时仍保留整组关系，不拆成大量孤立未匹配记录。
3. **退款冲销重付业务链**：识别原付款—退回—重付、原收款—退款—重新收款以及原分录—红字冲销—重记；保留每一原始行、时间顺序、最终净影响和跨期情况。只有正负同额但证据不足时只列线索。
4. **手续费净额关系**：使用“银行实收＝账面应收－手续费”“银行实付＝账面应付＋手续费”等专用公式；必须同时有费用文字和共同业务编号或对方证据，普通收付款不能用于凑平差额。
5. **重复记录识别**：区分相同流水号的强重复线索、流水号不同或缺失的同额重复疑点及正负同额线索；程序不删除、不合并原始记录。
6. **整批冲突求解**：先按共享源行拆分竞争组，小型竞争组寻找整体最优的不重叠组合，超大竞争组稳定降级；优先完整业务范围、强证据、金额闭合和较小剩余差异，避免较弱候选先占用记录。
7. **搜索范围公开**：报告披露竞争组数量、完整求解组数、降级组数、最大候选规模、中止状态和是否全部穷尽。搜索受限时不作排除性结论。
8. **审计底稿证据**：保留（当前作为隐藏附表）“退款冲销重付、手续费及净额、截止性差异、重复线索”等专题工作表；每个关系保留稳定匹配ID、双方原文件行号、笔数、收支、净额、差额、公式、业务依据、风险状态和其他合理解释。
9. **长任务持续可见**：生产核对和筛选导出都在后台完整执行，显示读取、候选生成、关系选择、报告构造、写入和完成进度；单个筛选步骤超过15秒会持续报告当前状态，避免界面假死。

## 一、最重要的处理原则

主界面有三个核心参数：

| 参数 | 默认值 | 用途 |
| --- | ---: | --- |
| 实际执行重要性水平 | 100,000 元 | 控制单项及月度累计事项的高风险分级和展示优先级 |
| 明显微小错报临界值 | 5,000 元 | 控制可量化小额差异是否自动归集为低风险事项，以及零差额弱证据小额匹配是否自动确认 |
| 自动确认最低综合可信度 | 70 | 在候选关系已经成立的前提下，控制普通候选的自动确认 |

程序按以下顺序分流：

1. 金额、方向和必要文字证据成立且关系唯一时，自动确认一对一、一对多、多对一或多对多关系。
2. 有业务编号、完整凭证、明确批次或同等强度的完整范围依据，且不存在硬冲突或跨月多对多、整个交易组收入和支出分别闭合时，输出“整组勾稽一致”，不虚构逐笔对应；只有账户、币种、期间和总额相同，不能证明业务边界。
3. 非零差异、跨期、关键字段冲突或候选歧义先计算影响金额，再按两个重要性阈值自动分级；这些事项仍会完成处理和输出。
4. 影响不超过明显微小错报临界值时，自动归集为低风险；超过该临界值但不超过实际执行重要性水平时为中风险；超过实际执行重要性水平时为高风险。
5. 零差额、影响不超过明显微小错报临界值、且疑点仅因综合可信度不足、业务依据不足或候选歧义的匹配，直接自动确认，判断依据注明"金额明显微小自动确认"及原始疑点原因；关键文字字段冲突、批次边界不足、跨月多对多或断档窗口内（范围未知）的除外。
6. 中风险疑点按最早交易日期排序等距抽样，抽中数量取中风险事项数与高风险事项数的较小值，高风险为零时抽零项；抽中项优先核查，未抽中项在全部核对明细中留存备查，技术附表保留原风险与抽样标记。高风险和范围未知事项全量核查，不参与抽样。
7. 明确定性高风险直接列为高风险；影响无法量化或核对范围身份冲突时列为“范围未知”。
8. 没有足够证据建立关系的记录分别进入“银行侧待查”或“日记账侧待查”，不会伪装成已匹配。
9. 所有状态都是程序的完整结果，不存在必须等待用户处理才能结束的状态。

匹配组金额采用双方绝对金额合计的较大者，不把收入和支出互相抵销。重要性水平只负责风险分级，不会单独证明两条记录属于同一业务。

## 二、金额方向

程序会根据文件来源分别解释借贷方向：

| 来源 | 增加 | 减少 |
| --- | --- | --- |
| 银行流水 | 贷方、收入、收、转入等 | 借方、支出、付、转出等 |
| 企业日记账 | 借方、收入、收等 | 贷方、支出、付等 |

因此，银行流水中的“贷”表示账户资金增加，“借”表示账户资金减少；企业日记账则按银行存款科目的借增贷减处理。

无法识别的方向不会默认当作收入。程序会记录解析异常，避免静默把正负号弄反。

## 三、输入检查

选择文件后，程序会自动分析表头位置、表头行数和派生列名。点击“开始核对”时，程序先执行输入检查，再进入正式匹配。该功能完全固化在程序代码中，不调用也不依赖外部表头识别 Skill。

输入检查包括十三项：

1. **文件读取**：文件是否存在、格式是否支持、能否读取及是否有可核对数据；
2. **表格结构**：表头位置、表头层级、合并单元格、派生列名和数据区域是否可靠；
3. **日期范围**：双方最早日期、最晚日期及范围差异；
4. **核对账户**：识别本方账号缺失、混合或双方冲突；
5. **核对币种**：识别币种缺失、混合或双方冲突；
6. **金额口径**：双方是否都使用原币或都使用本位币；显式声明还必须与实际选中的原币、本币、外币或记账本位币金额列一致，未注明时披露，明确不一致时停止；
7. **金额方向**：银行流水按贷增借减，银行日记账按借增贷减，并保留红字和原方向；
8. **金额合计**：收入、支出分别合计和比较，不用净额抵销替代；
9. **总体余额控制**：分别检查期初加期间净发生额是否等于期末、余额是否连续以及双方期初期末是否一致；
10. **非交易行**：合计、累计、统计、标题、重复表头、注释和空行；
11. **数据入口**：每个原始数据行只归入有效交易、非交易行、解析异常或其他排除之一；
12. **必填字段**：日期及当前金额模式所需的金额、借贷或方向列；
13. **辅助文字完整性**：摘要、对方户名及其他已选文字列的非空率。

检查结果分三级：

- **通过**：当前项目未发现影响使用的异常；
- **疑点**：日期范围不同、账户或币种字段缺失、金额口径未注明、收支合计有差额、存在非交易行、辅助文字不足或局部解析失败。程序记录疑点并自动继续；其中账户、币种、金额口径未验证、期间无法计算、解析异常或其他结构性缺口会限制总体范围；单纯双方期间或收支不同作为待查差异处理。可定位且覆盖不过半交易日的余额断档只降低窗口内关系，另一侧余额点不足等独立限制仍保留；
- **无法计算**：文件没有数据、必填映射无效、任一侧没有任何有效日期、金额或交易，已提供的账户、币种在单份文件内混合或双方明确不一致，或双方明确采用不同金额口径。程序在匹配前停止，单独生成“输入问题报告”，不会占用正式核对报告路径。

收入或支出差额本来就是核对对象，业务疑点不会弹出确认窗口，也不会擅自被判断为输入错误。原始银行流水和银行日记账始终只读，不会被覆盖或回写。

## 四、程序能匹配哪些情况

程序会统一生成候选、评分，再一次性选择互不冲突的结果。主要场景包括：

- 同日同金额的一对一；
- 日期容差内的一对一；
- 白名单业务，例如手续费、利息、工资、税费；
- 原表中物理相邻、标准化摘要一致的完整连续组，对应另一侧一笔合计记录；
- 一对多和多对一组合；
- 依据业务编号、同一完整年月的凭证字和凭证号或明确批次形成的非相邻完整组，双向支持；
- 工资、员工报销、供应商批量付款和客户批量收款等明确批量业务；双方笔数或总额不一致时，报告保留缺项、重复、补发或退回的核查线索；
- 同业务的多对多，例如银行150+450对应序时账100+200+300；
- 有完整业务范围依据的同月 3 对 5 等多对多整组核销；
- 同日总额和同月总额候选；没有批次、凭证、明确对方及具体用途等边界证据时，只能作为疑点或竞争组成；
- 相邻月份的一对一；
- 相邻月份的多对多候选，由程序按影响金额和定性证据自动分级；
- 金额存在明显微小差异的候选。
- 原付款、明确退回、再次付款，以及原收款、退款、重新收款形成的同侧业务链；每一原始行都保留，跨月或跨年时单列截止性差异；
- 银行实收等于账面应收减手续费、银行实付等于账面应付加手续费等净额关系；只有费用行有明确手续费、佣金、结算费等文字且业务编号或对方证据一致时才成立；
- 流水号相同且其他字段一致的强重复线索，以及日期、金额、对方和摘要相同但缺少共同流水号的同额重复疑点；程序不自动删除任何记录。

连续摘要整组支持“多笔银行流水对应一笔日记账”和“多笔日记账对应一笔银行流水”。程序按原表行号判断是否真正相邻，只取完整连续组，并限制组合日期跨度；摘要为空、原表行号中断、零金额不允许或收入支出方向不能分别对应时，不会生成这类候选。

默认配置不为任一侧全部为零的记录建立关系；只有明确启用“允许零金额匹配”时才允许。双方各自包含非零收入和支出、但净额恰好为零的完整组仍按收入和支出分别核对，不会被误当成纯零金额。

同日或同月总额核销会同时检查收入、支出的结构和金额分布，不会只看净额相等。明确不同业务、批次或对方的记录，不能因为总额相等就合并；只有宽泛的“收款、付款、货款”等摘要和同一主体，也不能证明多对多业务边界。有更充分业务依据的真实差额不能被弱依据的同额记录挤掉。同额确有多种合理去向时，报告保留竞争组成。

有明确范围的完整凭证组和批量业务组不受通用30笔组合深度限制。单张完整凭证可能命中大量同主体、同摘要银行行时，程序先按共同编号、明确主体和具体摘要、金额差、日期及稳定内容顺序缩小核验池，再逐组核验证据；业务完整组、凭证组和通用组合的潜在数量、实际保留数量及截断均写入运行参数。缺少业务分组依据时，通用组合仍受候选池、搜索深度、节点、单任务时间和全局时间预算约束。隐藏的核对结论与运行参数保留每类候选的完成和截断证据，主表用普通中文提示限制；出现限制时明确写“未找到对应不代表不存在组合”，不把未搜索到候选说成已经穷尽。

## 五、文字信息如何参与匹配

金额不是唯一依据。程序可以同时比较多列文字，包括：

- 摘要；
- 业务说明；
- 交易用途；
- 对方户名；
- 附言；
- 备注；
- 业务号、业务编号、批次号、批次编号、银企批量号、银企批次号、订单号、合同号、结算号；
- 交易流水号、回单号等辅助原始文字；
- 用户手动选择的其他文字列。

账号、卡号和凭证号不会默认作为辅助文字勾选。凭证字/类型与凭证号共同用于序时账侧的分组边界与原行展示；只有完整年月、凭证字、保留分隔符后的凭证号和收支方向相同的记录才属于同一凭证组。程序不会把同号凭证跨月、跨年或跨凭证字合并，也不会为了金额相等抽取凭证内部分分录。在日期窗内且整张凭证金额完整一致时，共同业务编号、共同交易流水或明确同一对方等跨双方依据可以支持闭合；只有相同具体摘要、没有共同业务编号、交易流水和明确对方时，只列为疑点。整张凭证存在合理金额差异时，仍保留整张凭证及差额，不改用部分分录凑平；金额超出普通金额窗时，必须有共同业务编号，或“明确对方＋具体摘要”等更强依据才能保留整张凭证候选。

批次号、业务编号用于界定一批业务；订单号、合同号等可以是批次内子项，同一批次包含多个订单时不会被拆散。Excel把数值型整数编号读成“123.0”时，程序按数值来源将其与文本“123”视为同号，同时在辅助文字中保留“123.0”原值；原本就是文本的“123.0”不会被改写，前导零和分隔符也不会丢失。供应商名称、收款单位、付款单位、对方单位、对手方和交易对手都按主体信息识别。每笔银行交易流水号或回单号只用于一对一交易核验：一对多或多对一时，双方都明确提供交易编号而编号集合不一致即列为冲突；工资或已有明确批次边界的汇总业务不因批次内逐笔流水号不同而拆散。编号缺失时，程序继续使用可用的日期、用途和对方信息，但不会只凭同额自动确认关系。

工资代发、供应商批付或客户批收的一侧可能只有银行平台或汇总单位，另一侧则列出员工、供应商或客户明细。双方有明确批次号，或都明确写明同类批量用途，且确实是一侧汇总、一侧明细时，主体集合不同会作为“汇总与明细层级不同”的核查线索保留，不作为普通交易对手冲突。普通逐笔、普通货款和没有批量边界的关系仍按明确主体冲突处理。

程序会记录哪些字段提供了支持、哪些字段存在冲突，并把金额分、日期分、文字分、结构分和综合可信度写入报告。

## 六、明显微小错报的月度累计

小额差异不是全年混在一起累计，而是按自然月分别累计。程序分成四个互不抵销的池：

- 银行侧独有收入；
- 银行侧独有支出；
- 日记账侧独有收入；
- 日记账侧独有支出。

每个池累计的是差异绝对额。某个月、某一池的累计值超过“实际执行重要性水平”时，该池及其组成项目自动升级为高风险疑点，程序仍正常完成并保留全部组成。其他月份和其他池不受影响。

## 七、大模型辅助

大模型是可选增强项，不是程序运行的必要条件。关闭大模型时，基础核对流程完整可用。

支持两种方式：

- 在线 API；
- 本机 LM Studio。

大模型只能在程序已经找到的候选中辅助比较文字语义，不能自行创造候选，也不能覆盖金额、重要性和跨月规则。调用失败、超时、返回格式错误或返回候选集外编号时，程序会自动退回本地评分并继续生成报告。

### 在线模式的隐私范围

在线模式只发送候选编号、日期、金额，以及摘要、业务说明、交易用途、附言、备注等允许的业务文字。账号、卡号、对方户名等敏感字段只在本机比较，在线端最多收到“相同/不同”的结论，不会收到字段原值；源文件路径和凭证号也不会发送。

### 本地模式的字段范围

本机 LM Studio 默认使用 `http://localhost:1234/v1`。除基础日期和金额外，只发送用户在“大模型辅助配置”中明确填写的本地字段。

### API 密钥

密钥只保存在当前程序会话的内存中，不写入配置文件、日志或 Excel。也可以使用环境变量：

- `BANK_RECONCILIATION_API_KEY`
- `OPENAI_API_KEY`

报告中的接口地址、错误信息和模型原始回答会先做脱敏处理。

## 八、安装和使用

### 首次安装

运行环境为 Windows 10 或 Windows 11，建议使用 Python 3.11 及以上版本。安装依赖后，直接双击 `启动银行流水核对工具.cmd`。也可以在项目目录运行：

```text
python -m pip install -r requirements.txt
python main.py
```

依赖清单已经包含桌面界面、Excel 读写、`.xls` 读取、数据处理和内存监控所需组件，不需要安装 Excel 插件或启用宏。以后再次使用时，只需双击 `启动银行流水核对工具.cmd`。需要生成独立 Windows 程序时，双击 `打包银行流水核对工具.cmd`，完成后使用 `dist\银行流水核对工具.exe`。

### 每次核对

1. 双击 `启动银行流水核对工具.cmd`，打开主窗口。
2. 选择一份银行流水和与其对应的一份银行日记账。程序会自动分析表头位置、表头行数和列名。
3. 如有需要，可调整“跳过”和“表头行数”，再使用“自动检测”。
4. 点击“配置列映射与辅助字段”，确认日期、金额方向和文字列。
5. 按项目情况调整“实际执行重要性水平”“明显微小错报临界值”和最低综合可信度。
6. 如有需要，打开“高级匹配参数”。
7. 如有需要，打开“大模型辅助（可选）—配置与测试”。
8. 点击“开始核对”。程序先执行十三项输入检查；业务疑点自动记录并继续，只有没有计算条件时才停止并生成独立输入问题报告。
9. 完成后，报告保存在银行流水文件所在目录，打开后先看“核对概览”；输入检查等证据保存在隐藏附表中。本次列映射和项目记录同时保存在本机，下次读取同样表头时自动套用。
10. “打开最近报告”可重新打开最后一次未被修改的报告；“筛选导出”可从全量报告另存审计筛选版；“生成模板”可生成银行流水和银行存款序时账两个标准模板。

运行过程中，进度条和运行日志会持续显示文件读取与有效行数、十个匹配阶段、每阶段新增及累计候选数、组合搜索已处理任务数、候选选择覆盖行数、报告构造与写入节点以及各段耗时。较长步骤没有新进度时，界面仍保留当前阶段，不会把文件刚创建或生产核对结束误报为整个验收已经结束。筛选导出同样在后台完整执行，显示读取、筛选、写入和完成进度；单个步骤超过15秒时会持续报告当前状态，界面不会因生成大型底稿而卡死。

报告文件名格式为：

```text
银行流水名_vs_日记账名_核对报告_时间戳.xlsx
```

支持 `.xlsx`、`.xls` 和 `.csv` 文件。

## 九、列映射模式

每份文件可独立选择：

- 借贷分列；
- 单列金额加方向；
- 单列金额含正负号。

至少要正确指定日期和金额相关列。摘要可以为空，但建议选择摘要、业务说明等文字列，以提高相同金额、多笔候选时的判断质量。

## 十、最终状态

报告使用五个正式状态：

- 自动确认；
- 整组勾稽一致；
- 自动归集事项；
- 疑点事项；
- 未找到候选。

状态描述程序已经完成了什么，风险等级另行使用“正常、低风险、中风险、高风险、范围未知”。“整组勾稽一致”只确认交易组整体闭合，不声称已经找到唯一逐笔关系。这些正式状态及原统计口径保留在技术附表；主表使用便于阅读的业务结果和事项说明。

## 十一、Excel 报告

每次核对只生成一份 Excel，默认显示三张主表。打开后先看概览，再查看需要复核的事项，最后按事项编号进入完整明细。

| 主表 | 看什么 | 怎样使用 |
| --- | --- | --- |
| 核对概览 | 账户与期间、双方记录笔数、核对结果、待复核事项、跨期提示、资料与余额情况 | 点击“查看位置”进入对应主表；已核对业务仍可能存在期间问题 |
| 待复核事项 | 一项业务需要关注的问题、双方事实和核查建议 | 点击事项编号直接定位全部明细；后续状态和处理说明可以不填 |
| 全部核对明细 | 双方日期、摘要、交易对方、业务编号、金额和原始出处 | 逐笔关系并排看；整组先看合计，再用左侧展开按钮查看双方全部组成 |

同一明确业务关系的金额差异与跨期问题合并列示，不因出现在不同专题重复要求处理。低风险和未抽中的中风险留存备查，原有风险分级和抽样名单不变。跨期提示独立保留，即使金额很小且已自动确认，仍会提示核查入账期间。

主表金额正数为收入、负数为支出。整组“业务合计”和下方“组成记录”是同一批金额的两种展示，不能重复加总；组内记录分别列出，不把未知的逐笔对应画成确定配对。来源列保留文件、工作表和原始行号。

例如，银行 2025 年 12 月 31 日收到服务费 3,000 元，账上 2026 年 1 月 1 日记录同额收款：概览显示跨期事项，待复核表写明需要核查入账期间，点击编号即可看到双方日期、金额和出处。

### 技术附表

评分、候选编号、稳定键、组成键、运行参数和解析细节保留在同一个工作簿的隐藏附表中。需要排查时，在 Excel 中右击工作表标签，选择“取消隐藏”。原“核对结论、疑点事项、逐笔匹配、整组勾稽、匹配组成、截止性差异、输入检查、运行资料与映射、数据入口处置”等证据表继续保留。附表名称和字段便于追溯，不作为日常阅读入口。

隐藏技术字段不等于隐藏重要限制：范围受限、余额核对未实施、余额异常、其他可能对应和搜索未穷尽等影响判断的信息仍会在主表说明。没有内容的专题不会额外显示；没有待复核事项时明确写出无事项。

### 可选后续标注

在“待复核事项”选择“已关注、已处理、无需处理”，并按需要填写处理说明。“核对概览”的已处理事项数通过普通 Excel 公式更新，无须宏、插件或回传。完全不填写时报告仍然完整。人工填写不改变程序最初的匹配与风险判断。

### 项目历史、映射模板和筛选导出

- 每次成功核对后保存输入与报告的路径、指纹、映射、参数和结果；历史或模板未能保存时提示已生成报告的路径。历史报告修改后仍按现有规则提示记录失效。
- 同样表头再次导入时自动套用列映射，并重新检查账户、币种、期间和金额方向。
- 筛选支持金额覆盖比例、日期、摘要或对方包含/排除、业务类型、结论状态和差异原因。选中业务内任意记录时，双方完整组成一起带出。
- 新格式筛选版仍只显示三张主表，重新计算本次选中记录和待复核事项数，条件使用普通中文说明。全局资料与余额限制继续保留，并注明来自全量报告；隐藏的原统计证据仍是全量口径。
- 筛选版另存，不能覆盖原全量报告，包括不同名称实际指向同一个文件的情形。旧格式历史报告继续按原入口打开及筛选，不批量改写历史文件。
- 历史和模板默认保存在 `%LOCALAPPDATA%\银行流水核对工具`，本轮不提供删除历史功能。

## 十二、高级参数

大多数项目保持默认值即可。常用参数包括：

- 日期容差：普通一对一允许跨日或跨月的天数；
- 组合窗口：组合候选可跨越的最大日期范围；
- 组合最大深度：单个组合允许包含的最大笔数；
- 批量最少笔数：工资、代发等批量场景的起始门槛；
- 每笔最大候选数：限制候选爆炸；
- 内存限制：内存偏高时自动降级为更保守的处理方式；
- 随机种子：`0` 等固定值便于复现；`-1` 表示每次使用新的实际种子，报告会同时记录请求值和实际值。

停止按钮会通知匹配器尽快结束。已生成的原始文件不会被改动。

- 中风险疑点按最早交易日期排序等距抽样，抽中数量与高风险事项数一致：抽中项优先核查，未抽中项仍在疑点事项表完整列示，但建议动作标注"等距抽样未抽中，随同低风险留存备查，本次不留人工"。高风险和范围未知事项全量核查，不参与抽样。
- 核对结论总览新增"中风险抽样总数"和"中风险抽中待核查数"两行；"截止性差异"表来自业务链跨期标记，不受自动确认影响，跨期小额配对仍照常列示。
- 本轮取代 2026-08-09 设计的"候选歧义必须挡住明显微小自动确认"规则，取代范围仅限零差额且金额不超过明显微小临界值；需求、设计与审查见 `docs/requirements/2026-09-06-疑点分层处置-requirement.md`、`docs/superpowers/specs/2026-09-06-疑点分层处置-design.md`、`docs/reviews/2026-09-06-疑点分层处置-review.md`。

### 2026-09-06：余额断档局部降级

- 余额连续性断档不再触发整体降级。断档能定位到具体日期时，只有"断档窗口"（断档日＋前一有记录交易日，即两个余额锚点之间）涉及的匹配关系降为疑点、范围未知；窗口外已精确对平的关系正常自动确认。断档无法定位或窗口覆盖过半交易日时，回退整体降级。
- 系统结论和输入检查改为披露断档日期与受影响窗口（例如"余额在2025-07-01断档，仅断档窗口内关系降为疑点"），不再笼统写"总体余额控制异常、全部降为疑点"。
- 领域文档新增"断档窗口"词条，决策记录见 `docs/adr/0003-余额断档局部降级.md`。

### 2026-09-06：独立复核修复

- 两侧全部对应时，待查工作表不再多出一行全空行（排版不再触碰空表第2行）。
- 双方起止日期不一致、收支合计不一致属于正常未达事项和核对对象本身，不再单独把全部关系降为疑点；只有期间或收支无法计算、账户/币种/金额口径未通过验证、存在解析异常或其他排除行等结构性问题时，才限制总体范围并把受影响关系降为疑点、范围未知。
- 待查表中已纳入同侧业务链的记录，判断依据直接写明业务链编号，并指引到"退款冲销重付"表整体核查，不再与无候选记录混同。
- 余额连续性改为日界勾稽：同一自然日内文件行顺序不代表过账顺序，不再逐行误报；日内勾稽不稳时按余额排序重放一次，能闭合的视为行序噪声，仍不闭合的按原行披露。真实流水中的月份交界断档仍能定位到具体日期。
- 真实数据验证（东方农博民生银行，流水 2,509 行对序时账 2,633 行，端到端 396 秒）：余额连续性异常由 54 处误报降为 2 处真实断档（2025-07-01 缺行 -499,558.37、2026-07-01 缺行 +316,072.25），其余产出逐项稳定；详见 `docs/reviews/2026-09-06-全面升级独立复核-review.md` 第八节。
- 工作表"数据人口处置"更正为"数据入口处置"，输入检查同名项目和相关说明文字一并更正。

### 2026-09-06：单账户审计核对第三至第六阶段

- 新增退款、退汇、冲销和重付同侧业务链。只有金额方向、对方或业务编号、退回文字与日期先后共同支持时才识别；正负同额但缺少证据的记录只列线索。
- 新增手续费净额关系，明确展示总额、费用、净额、关系公式和公式差额；普通收支即使金额刚好也不能充当手续费。
- 新增强重复、同额重复疑点和跨期业务链专题工作表，不删除、不合并任何原始记录。
- 候选选择按共享源行拆成竞争组，小组内整体寻找最优不重叠组合；大组稳定降级，求解组数、上限、中止和是否穷尽写入运行参数。
- 新增列映射模板、核对项目历史、报告指纹校验、整组筛选导出、标准输入模板、Windows 双击入口和独立程序打包脚本；主界面可打开最近报告、生成模板和另存筛选底稿。
- 报告新增“退款冲销重付、手续费及净额、截止性差异、重复线索”，关系主表补充净额公式字段。

### 2026-09-05：单账户审计核对第一、二阶段审查版本

- 长时间真实项目运行增加可见进度：显示当前阶段、处理数量、候选数量和分段耗时；匹配器进度按30%—75%线性映射到整项任务，报告构造、写入和排版保存分别留痕。
- 账户、币种、原币/本位币口径的明确冲突在 Matcher 启动前阻断，并留下独立输入问题报告；字段部分缺失或金额口径未注明时继续处理，但总体资料标为尚未闭合，所有具体关系降为范围未知疑点。
- 数据入口按原文件行唯一归类，报告绑定文件 SHA-256、工作表、表头和列映射；超过1000条解析异常也不再截断入口计数，存在解析异常或其他排除行时总体资料直接标为尚未闭合，并把相关关系降为范围未知。
- 余额连续性、期初加净发生额等于期末及双方起止期间前移到匹配前；总体控制异常时，相关关系降为范围未知疑点。
- 支持35笔以上完整凭证组、工资和明确批量收付，不受通用30笔组合候选上限截断；明确批次号存在差额时同样列出两侧笔数、差额和缺项或重复核查线索。完整凭证金额差异超过实际执行重要性水平时，只有共同编号或“明确对方＋具体摘要”等强业务证据才能越过普通金额窗保留整张凭证；缺项、重复或批次边界不足时保留整批线索并降级。
- 完整凭证按年月、凭证字、凭证号和方向共同成键并禁止切片；批次内订单号与交易级流水号按各自层级使用，避免把真实批次拆散。
- 批次明细与汇总的笔数不直接相减为“缺多少笔业务”；金额差可按常见单笔金额给出测算线索，但明确写明不能据此确定缺项、重复、补发或退回。
- 公开关系号改由业务内容组成生成，候选池截断也按内容稳定排序，换行不改变候选集合和关系号；密集多解按关系最多保存10套稳定竞争样本，同时完整披露竞争组总数，避免数千行输入造成平方级报告膨胀。
- 精确、容差、白名单、凭证和组合等候选阶段统一记录完成、截断、节点及时间预算；大量同额的一对一精确候选不会被误算为补充组合池截断，真正未穷尽时报告首页直接披露搜索受限并不作排除性结论。
- 借方、贷方两格同时为空的有效日期行列为金额解析异常并保留原行证据，不再补成零金额交易；明确填写零仍保留原值，但默认不建立纯零金额关系，只有启用允许零金额匹配时才参与。
- 本版本之后已由 2026-09-06 第三至第六阶段完成上述专题和使用闭环。

### 2026-08-29：自动化优先与人类友好输出

- 正式状态扩展为“自动确认、整组勾稽一致、自动归集事项、疑点事项、未找到候选”，另行使用五级风险；业务疑点不再成为必须人工处理或阻断程序的条件。
- 多个合理拆分但整个交易组闭合时自动形成组级结论；明显微小错报临界值和实际执行重要性水平只负责风险分流，不负责证明匹配关系。
- 输入检查扩展到账户、币种和数据入口；当前版本进一步扩展为十三项，只有客观上没有计算条件时停止。
- 报告改为结论和事项优先，机器字段及技术工作表默认隐藏；首页同时汇总数量和金额，并提供三项建议动作。
- 可选后续状态允许留空，主动填写后首页公式自动更新；外来表头和单元格文字均执行公式注入防护。
- 修复全空余额列被当成零并伪造余额轨迹的问题；匹配组成中的交易金额改为正数并单列收支方向；零影响事项显示为正常风险。

### 2026-08-09：匹配可靠性与交付补强

- 清理旧报告器、旧倒排索引、旧匹配 worker、旧白名单直写链路及其他无调用实现，正式流程统一收敛到候选生成、评分、选择和风险分流主链。
- 关键文字字段冲突和候选多去向保留为结构化证据；当前版本由程序按影响金额和定性规则自动分级并继续输出。
- 新增双向“连续摘要整组”候选，使用原表行号判断物理连续，并检查日期窗口、零金额规则以及收入、支出分别一致。
- 新增 `requirements.txt` 和 Windows 安装说明，不需要 Excel 插件、VBA 或宏。
- 补齐连续摘要类型的中文报告展示，以及空摘要、行号中断、摘要不同、收支抵销、日期超窗等边界测试；全量自动测试增至 206 项。

### 2026-08-08：自包含输入检查基础

- 固化复杂表头识别能力，可处理标题行、1 至 3 行复合表头、合并单元格、派生列名和结构歧义，不依赖外部 Skill。
- 最初建立文件读取、表格结构、日期范围、金额方向、收支合计、非交易行、必填字段和辅助文字完整性八项检查；当前版本已扩展为十三项。
- 当前版本把结果统一为“通过、疑点、无法计算”：业务疑点自动继续，收入和支出分别比较，不用净额抵销。
- 明确一份银行流水只对应一份银行日记账，不提供多银行流水合并。
- 最终 Excel 报告包含“输入检查”工作表，原始输入文件保持只读。

- 请保留银行流水、日记账原文件和最终报告。

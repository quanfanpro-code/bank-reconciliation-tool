# 银行流水核对工具 v3.2

[![License: AGPL v3](https://img.shields.io/badge/License-AGPL_v3-blue.svg)](https://www.gnu.org/licenses/agpl-3.0)

这是一个面向审计项目的 Windows 桌面工具。每次核对接收一个银行账户的流水及其对应的银行存款序时账（旧界面和报告中也称“日记账”）。当前集中处理单账户的逐笔、合并拆分、批量收付款、退款退汇、冲销重付、手续费净额、重复线索和跨期关系，不做多文件合并、多账户批量或企业财务月度对账。程序自动生成对应关系、组级结论和疑点明细，不要求先填写人工结论才能出报告。

## 快速开始

1. 首次使用按第八节安装依赖，之后双击 `启动银行流水核对工具.cmd` 打开当前源码版本。已有的独立 EXE 不会随源码提交自动更新；需要使用新功能时请运行当前源码版本。
2. 选择同一账户的银行流水和银行存款序时账，检查列映射、金额方向及核对参数。
3. 点击“开始核对”，完成后在银行流水所在文件夹取得 Excel 报告。
4. 先看“核对总览”、月度和每日差额，需要人工核对时在“待处理事项”的黄色格选择结果并保存。

## 当前报告：一个文件，阅读和留痕分区

前五张表依次为“核对总览”“待处理事项”“月度核对”“每日统计”“对应明细”，后接“事项证据”“每日差异证据”和“非工作日交易”。总览顶部醒目显示本次实际执行重要性水平、明显微小错报临界值及处置含义；待处理事项仅列全查及实际抽中事项，每项只在一个黄色格填写，备查不混入待办。

每项待办直接列出双方实际业务、金额及组成合计、程序归纳的差异、具体待答问题及黄色填写格；点击“查看完整证据”定位到本项原始交易，每笔只在本表列一次，可直接返回填写格。其他候选方案集中在“其他对应供选择”，从事项证据的“其他方案”列跳转；人工复核表每套候选只列一行摘要，不再重复展开全部交易。候选方案可能反复引用同一原始记录，不代表新增交易。浅绿色计算和追溯表默认隐藏，原始记录与旧版计算公式继续保留。

月度核对保持现有结构和数值；每日统计保持原有结构，T列“需查看”写明收支/余额具体差额、笔数拆分或跨日核查原因，点击即到当日双方完整记录及相关事项。非工作日交易仍直接可见。重要性仅影响风险、全查/抽样/备查及展示，不得替代业务匹配证据；候选搜索窗与两项审计阈值独立。

详细操作与指标口径见第十一节。

## 2026年10月22日：合计、累计行清理补强

银行流水和明细账统一识别明确的合计、累计、小计、总计等汇总行，在日期补齐和金额计算前排除。标签可以位于月份、日期、摘要或其他列，支持“9月合计：”“本期累计:”等写法；无有效日期的明确汇总行，即使凭证位置填有统计笔数，也不会作为交易重复计算。

正常业务描述如“累计结算货款”“支付项目合计款”和普通日期续行继续保留，不能仅因包含关键词就排除；日期无法解析且没有明确汇总标签时，仍记录解析异常。原文件不改，原始行号、原始值和排除原因可在“数据入口处置”“解析异常明细”中追溯，输入检查与清理采用同一汇总判断。

## 2026年9月24日：非工作日银行收付示警

程序只检查银行流水中有效、金额非零的收款和付款：所选银行日期落在全国统一放假日或普通周末，即逐笔列入“非工作日交易”；调休上班的周末不列入。即使该笔流水已与银行存款序时账核对相符，示警仍保留。序时账录入日期不参与判断，也不因示警改变原有匹配结果或风险分级。

首页显示示警总笔数、收付款各自的笔数和金额，以及超出日历范围的银行交易笔数。明细保留银行原文件行号、所用交易日期、原日期列名和值、休息日类型、节日名称、收支方向、金额、摘要及可用的对方辅助文字。银行文件若只提供入账日或记账日，示警仅表示该列日期落在休息日，不证明付款指令在当天发出。示警是审计关注线索，具体原因仍需结合回单、审批和交易背景核查。

日历内置 2021—2026 年全国放假调休安排，运行不需联网。超出这六年的日期不按普通工作日处理，首页明确显示“银行交易日历未覆盖笔数”；应更新对应年度日历后再判断。依据为国务院办公厅的 [2021年](https://app.www.gov.cn/govdata/gov/202011/25/465322/article.html)、[2022年](https://app.www.gov.cn/govdata/gov/202110/25/477428/article.html)、[2023年](https://app.www.gov.cn/govdata/gov/202212/08/495070/article.html)、[2024年](https://app.www.gov.cn/govdata/gov/202310/25/508678/article.html)、[2025年](https://www.gov.cn/zhengce/zhengceku/202411/content_6986383.htm)、[2026年](https://www.gov.cn/zhengce/zhengceku/202511/content_7047091.htm)部分节假日安排通知。

### 没有照搬的算法及原因

反编译和场景复核发现，对方工具存在以下不适合审计直接采用的做法：

1. 宽松模式可能只凭账户和金额建立对应，日期、对方和摘要不一致也可能通过。
2. 重复金额可能按原表先后顺序占用，没有把真实多解作为疑点保留。
3. 同月汇总没有完整区分年份，存在跨年度同月合并风险。
4. 一借一贷或一正一负同额可能被误当成冲销，缺少共同业务证据。
5. 一对多搜索先截取部分大额记录、限制组合笔数并在首个结果处停止，可能漏掉正确完整组。
6. 金额或日期解析失败、空账户和界面参数传递存在失真风险。

因此，本工具没有复制其宽松确认、顺序抢占、错误冲销、静默解析和有限首解搜索。

### 按审计业务重新完成的核心提升

1. **单账户范围控制**：一次只核对一份银行流水和对应的一份银行存款序时账；检查账户、币种、期间、金额方向、原始人口和余额连续性。明确冲突时阻止错误确认，资料不能完整证明范围时降低结论等级。
2. **拆分合并和批量业务**：加强一对多、多对一、多对多、工资、奖金、报销、供应商批付、客户批收、税费和社保等业务；优先依据完整凭证、业务编号、批次号、日期、对方和摘要确定业务边界。批次缺项或存在差额时仍保留整组关系，不拆成大量孤立未匹配记录。
3. **退款冲销重付业务链**：识别原付款—退回—重付、原收款—退款—重新收款以及原分录—红字冲销—重记；保留每一原始行、时间顺序、最终净影响和跨期情况。只有正负同额但证据不足时只列线索。
4. **手续费净额关系**：使用“银行实收＝账面应收－手续费”“银行实付＝账面应付＋手续费”等专用公式；必须同时有费用文字和共同业务编号或对方证据，普通收付款不能用于凑平差额。
5. **重复记录识别**：区分相同流水号的强重复线索、流水号不同或缺失的同额重复疑点及正负同额线索；程序不删除、不合并原始记录。
6. **整批冲突求解**：先按共享源行拆分竞争组，小型竞争组寻找整体最优的不重叠组合，超大竞争组稳定降级；优先完整业务范围、强证据、金额闭合和较小剩余差异，避免较弱候选先占用记录。
7. **搜索范围公开**：报告披露竞争组数量、完整求解组数、降级组数、最大候选规模、中止状态和是否全部穷尽。搜索受限时不作排除性结论。
8. **审计底稿重构**：新增“退款冲销重付、手续费及净额、截止性差异、重复线索”等专题工作表；每个关系保留稳定匹配ID、双方原文件行号、笔数、收支、净额、差额、公式、业务依据、风险状态和其他合理解释。
9. **长任务持续可见**：生产核对在后台完整执行，显示读取、候选生成、关系选择、报告构造、写入和完成进度；单个步骤超过15秒会持续报告当前状态，避免界面假死。

## 一、最重要的处理原则

主界面的“审计策略”模块放置四个常用参数：

| 参数 | 默认值 | 用途 |
| --- | ---: | --- |
| 实际执行重要性水平 | 100,000 元 | 控制单项及月度累计事项的高风险分级和展示优先级 |
| 明显微小错报临界值 | 5,000 元 | 不超过该值的可量化疑点按低风险备查；月度累计超限可升级；小额不证明匹配 |
| 日期容差（天） | 31 | 普通逐笔对应允许的日期相差天数；扩大范围只增加查找机会，不代表已经匹配 |
| 组合窗口（天） | 31 | 多笔合并时允许的日期跨度；与逐笔对应的日期容差分别设置 |

“自动确认分数门槛”放在高级设置中，默认70，满分100。普通候选达到门槛，且业务依据充分、没有冲突或歧义，才可能自动确认；70分不表示70%的准确率。分数门槛与重要性水平用途不同，分数不能覆盖明确的业务冲突。

程序按以下顺序分流：

1. 金额、方向及必要文字证据成立且关系明确时，自动确认；有完整业务范围、两侧收入支出分别闭合时，可以形成“整组勾稽一致”，不虚构唯一逐笔关系。已经明确自动确认的大额交易不再重复进入人工全查。
2. 对存在金额差异的已选关系，没有其他关系疑点时按差异金额分级；存在候选歧义、关键字段冲突或业务边界问题时，按涉及的组金额分级。组金额采用双方绝对金额合计的较大值，收入、支出不抵销。
3. 影响不超过明显微小错报临界值时为低风险；超过该临界值但不超过实际执行重要性水平时为中风险；超过实际执行重要性水平时为高风险。刚好等于实际执行重要性水平不算超过。
4. 零差额但评分或业务依据不足、存在歧义时仍为疑点，重要性只决定处置方式。大额充分确认事项不重复全查。明示原凭证、同日反向金额及完整摘要相同且唯一的账内冲销重记，归为闭合更正备查，原始收支和月度差额仍保留。
5. 银行侧或序时账侧未对应记录按可量化的交易金额分级；完整同侧退款、冲销、重付链保留全部组成，按收支绝对金额合计衡量影响，不冒充跨双方已确认。只有真实总体范围限制或涉及余额断档窗口的记录列为“范围未知”，不再把所有单边记录无差别标为范围未知。
6. 原有金额差异与新增单边记录先按自然年月、来源和收支方向累计；累计升级后，高风险和范围未知事项进入“人工全查”。
7. 完整中风险总体包含已选疑点、金额差异及未对应事项，按最早交易日期排序等距抽样。样本数为中风险事项数与高风险事项数的较小值；范围未知不计入高风险样本数基数；没有高风险时抽零项。抽中进入“人工抽样”，未抽中及低风险留存备查，不计入未核对待办。
8. 跨月、跨年事实单独保留。程序或人工确认对应关系，不会使期间差异消失。重要性水平只分配核对重点，不能证明交易属于同一业务。

程序先完成自动分析并生成报告；人工结果空白不表示程序尚未运行完。

## 二、金额方向

程序会根据文件来源分别解释借贷方向：

| 来源 | 增加 | 减少 |
| --- | --- | --- |
| 银行流水 | 贷方、收入、收、转入等 | 借方、支出、付、转出等 |
| 企业日记账 | 借方、收入、收等 | 贷方、支出、付等 |

因此，银行流水中的“贷”表示账户资金增加，“借”表示账户资金减少；企业日记账则按银行存款科目的借增贷减处理。

无法识别的方向不会默认当作收入。程序会记录解析异常，避免静默把正负号弄反。

## 三、输入检查

选择文件后，程序会自动分析表头位置、表头行数和派生列名。点击“开始核对”时，程序先执行输入检查，再进入正式匹配。该功能完全固化在程序代码中，不调用也不依赖外部表头识别 Skill。

输入检查包括十三项：

1. **文件读取**：文件是否存在、格式是否支持、能否读取及是否有可核对数据；
2. **表格结构**：表头位置、表头层级、合并单元格、派生列名和数据区域是否可靠；
3. **日期范围**：双方最早日期、最晚日期及范围差异；
4. **核对账户**：识别本方账号缺失、混合或双方冲突；
5. **核对币种**：识别币种缺失、混合或双方冲突；
6. **金额口径**：双方是否都使用原币或都使用本位币；显式声明还必须与实际选中的原币、本币、外币或记账本位币金额列一致，未注明时披露，明确不一致时停止；
7. **金额方向**：银行流水按贷增借减，银行日记账按借增贷减，并保留红字和原方向；
8. **金额合计**：收入、支出分别合计和比较，不用净额抵销替代；
9. **总体余额控制**：分别检查期初加期间净发生额是否等于期末、余额是否连续以及双方期初期末是否一致；
10. **非交易行**：合计、累计、统计、标题、重复表头、注释和空行；
11. **数据入口**：每个原始数据行只归入有效交易、非交易行、解析异常或其他排除之一；
12. **必填字段**：日期及当前金额模式所需的金额、借贷或方向列；
13. **辅助文字完整性**：摘要、对方户名及其他已选文字列的非空率。

检查结果分三级：

- **通过**：当前项目未发现影响使用的异常；
- **疑点**：日期范围不同、账户或币种字段缺失、金额口径未注明、收支合计有差额、存在非交易行、辅助文字不足或局部解析失败。程序记录疑点并自动继续；其中账户、币种、金额口径未验证、期间无法计算、解析异常或其他结构性缺口会限制总体范围；单纯双方期间或收支不同作为待查差异处理。可定位且覆盖不过半交易日的余额断档只降低窗口内关系，另一侧余额点不足等独立限制仍保留；
- **无法计算**：文件没有数据、必填映射无效、任一侧没有任何有效日期、金额或交易，已提供的账户、币种在单份文件内混合或双方明确不一致，或双方明确采用不同金额口径。程序在匹配前停止，单独生成“输入问题报告”，不会占用正式核对报告路径。

收入或支出差额本来就是核对对象，业务疑点不会弹出确认窗口，也不会擅自被判断为输入错误。原始银行流水和银行日记账始终只读，不会被覆盖或回写。

## 四、程序能匹配哪些情况

程序会统一生成候选、评分，再一次性选择互不冲突的结果。主要场景包括：

- 同日同金额的一对一；
- 日期容差内的一对一；
- 白名单业务，例如手续费、利息、工资、税费；
- 原表中物理相邻、标准化摘要一致的完整连续组，对应另一侧一笔合计记录；
- 一对多和多对一组合；
- 依据业务编号、同一完整年月的凭证字和凭证号或明确批次形成的非相邻完整组，双向支持；
- 工资、员工报销、供应商批量付款和客户批量收款等明确批量业务；双方笔数或总额不一致时，报告保留缺项、重复、补发或退回的核查线索；
- 同业务的多对多，例如银行150+450对应序时账100+200+300；
- 有完整业务范围依据的同月 3 对 5 等多对多整组核销；
- 同日总额和同月总额候选；没有批次、凭证、明确对方及具体用途等边界证据时，只能作为疑点或竞争组成；
- 相邻月份的一对一；
- 相邻月份的多对多候选，保留期间及业务依据，由程序按现行影响金额和范围限制规则分级；
- 金额存在明显微小差异的候选。
- 原付款、明确退回、再次付款，以及原收款、退款、重新收款形成的同侧业务链；每一原始行都保留，跨月或跨年时单列截止性差异；
- 银行实收等于账面应收减手续费、银行实付等于账面应付加手续费等净额关系；只有费用行有明确手续费、佣金、结算费等文字且业务编号或对方证据一致时才成立；
- 流水号相同且其他字段一致的强重复线索，以及日期、金额、对方和摘要相同但缺少共同流水号的同额重复疑点；程序不自动删除任何记录。

连续摘要整组支持“多笔银行流水对应一笔日记账”和“多笔日记账对应一笔银行流水”。程序按原表行号判断是否真正相邻，只取完整连续组，并限制组合日期跨度；摘要为空、原表行号中断、零金额不允许或收入支出方向不能分别对应时，不会生成这类候选。

默认配置不为任一侧全部为零的记录建立关系；只有明确启用“允许零金额匹配”时才允许。双方各自包含非零收入和支出、但净额恰好为零的完整组仍按收入和支出分别核对，不会被误当成纯零金额。

同日或同月总额核销会同时检查收入、支出的结构和金额分布，不会只看净额相等。明确不同业务、批次或对方的记录，不能因为总额相等就合并；只有宽泛的“收款、付款、货款”等摘要和同一主体，也不能证明多对多业务边界。有更充分业务依据的真实差额不能被弱依据的同额记录挤掉。同额确有多种合理去向时，报告保留竞争组成。

有明确范围的完整凭证组和批量业务组不受通用30笔组合深度限制。单张完整凭证可能命中大量同主体、同摘要银行行时，程序先按共同编号、明确主体和具体摘要、金额差、日期及稳定内容顺序缩小核验池，再逐组核验证据；业务完整组、凭证组和通用组合的潜在数量、实际保留数量及截断均写入运行参数。缺少业务分组依据时，通用组合仍受候选池、搜索深度、节点、单任务时间和全局时间预算约束。核对结论公开每类候选是否完成、是否截断或预算耗尽；出现限制时明确写“未找到对应不代表不存在组合”，不把未搜索到候选说成已经穷尽。

## 五、文字信息如何参与匹配

金额不是唯一依据。程序可以同时比较多列文字，包括：

- 摘要；
- 业务说明；
- 交易用途；
- 对方户名；
- 附言；
- 备注；
- 业务号、业务编号、批次号、批次编号、银企批量号、银企批次号、订单号、合同号、结算号；
- 交易流水号、回单号等辅助原始文字；
- 用户手动选择的其他文字列。

账号、卡号和凭证号不会默认作为辅助文字勾选。凭证字/类型与凭证号共同用于序时账侧的分组边界与原行展示；只有完整年月、凭证字、保留分隔符后的凭证号和收支方向相同的记录才属于同一凭证组。程序不会把同号凭证跨月、跨年或跨凭证字合并，也不会为了金额相等抽取凭证内部分分录。在日期窗内且整张凭证金额完整一致时，共同业务编号、共同交易流水或明确同一对方等跨双方依据可以支持闭合；只有相同具体摘要、没有共同业务编号、交易流水和明确对方时，只列为疑点。整张凭证存在合理金额差异时，仍保留整张凭证及差额，不改用部分分录凑平；金额超出普通金额窗时，必须有共同业务编号，或“明确对方＋具体摘要”等更强依据才能保留整张凭证候选。

批次号、业务编号用于界定一批业务；订单号、合同号等可以是批次内子项，同一批次包含多个订单时不会被拆散。Excel把数值型整数编号读成“123.0”时，程序按数值来源将其与文本“123”视为同号，同时在辅助文字中保留“123.0”原值；原本就是文本的“123.0”不会被改写，前导零和分隔符也不会丢失。供应商名称、收款单位、付款单位、对方单位、对手方和交易对手都按主体信息识别。每笔银行交易流水号或回单号只用于一对一交易核验：一对多或多对一时，双方都明确提供交易编号而编号集合不一致即列为冲突；工资或已有明确批次边界的汇总业务不因批次内逐笔流水号不同而拆散。编号缺失时，程序继续使用可用的日期、用途和对方信息，但不会只凭同额自动确认关系。

工资代发、供应商批付或客户批收的一侧可能只有银行平台或汇总单位，另一侧则列出员工、供应商或客户明细。双方有明确批次号，或都明确写明同类批量用途，且确实是一侧汇总、一侧明细时，主体集合不同会作为“汇总与明细层级不同”的核查线索保留，不作为普通交易对手冲突。普通逐笔、普通货款和没有批量边界的关系仍按明确主体冲突处理。

程序会记录哪些字段提供了支持、哪些字段存在冲突，并把金额分、日期分、文字分、结构分和综合可信度写入报告。

## 六、差异和未对应记录的月度累计

同一自然年月内，按来源及收支方向分别累计四类差异：银行侧收入、银行侧支出、序时账侧收入、序时账侧支出。不同年份、月份、来源、收入和支出之间不抵销。

已选关系沿用老版差异池组成；新增单边按每条原记录的真实年月、来源和收支方向加入对应累计。同侧业务链虽然作为一个复核事项展示，累计仍按其各条原记录分月、分方向计算。某池超过实际执行重要性水平时，其相关组成事项升级为高风险，然后再计算中风险抽样数量。

这项累计用于分配人工核对范围，不代替“月度核对”中的全量发生额及余额比较。“月度核对”始终按两份输入的原始有效记录汇总；人工选择不改变这些原始数字。

## 七、大模型辅助

大模型是可选增强项。GUI启动时自动读取本机保存的默认配置，并按该配置启用；没有本机配置时保持关闭。主界面显示实际启用状态和模型名称，关闭后基础核对流程仍完整可用。

支持两种方式：

- 在线 API；
- 本机 LM Studio。

大模型只能在程序已经找到的候选中辅助比较文字语义，不能自行创造候选，也不能覆盖金额、重要性和跨月规则。调用失败、超时、返回格式错误或返回候选集外编号时，程序会自动退回本地评分并继续生成报告。

### 在线模式的隐私范围

在线模式只发送候选编号、日期、金额，以及摘要、业务说明、交易用途、附言、备注等允许的业务文字。账号、卡号、对方户名等敏感字段只在本机比较，在线端最多收到“相同/不同”的结论，不会收到字段原值；源文件路径和凭证号也不会发送。

### 本地模式的字段范围

本机 LM Studio 默认使用 `http://localhost:1234/v1`。除基础日期和金额外，只发送用户在“大模型辅助配置”中明确填写的本地字段。

### API 密钥

已设置本机默认连接时，程序从 `C:\Users\27651\AppData\Local\银行流水核对工具\大模型默认配置.json` 读取连接参数和密钥；其他Windows用户使用各自的本机应用数据目录。该个人配置不在项目仓库内，不随GitHub提交同步。密钥不写入日志或Excel。

个人EXE在打包时把此配置内置到程序，运行时优先使用内置值，无需另带JSON文件。密钥可以从EXE中提取，内置不等于加密保密；指定HTTP接口也不提供HTTPS传输加密。该EXE只在本机交付，不上传GitHub；仓库不包含个人密钥。

本机已配置Qwen3.8-27B在线服务，默认启用，使用Chat Completions协议，等待上限600秒，每次最多5个候选。打开“大模型辅助（可选）—配置与测试”可以查看或修改。现有“保存当前会话配置”只影响本次运行，关闭程序后不会覆盖本机默认配置；下次启动重新读取默认值。启动读取配置不会自动发送业务数据。

也可以使用原有环境变量提供密钥：

- `BANK_RECONCILIATION_API_KEY`
- `OPENAI_API_KEY`

报告中的接口地址、错误信息和模型原始回答会先做脱敏处理。

## 八、安装和使用

### 首次安装

当前源码包含2026年10月12日的输出更新。本次没有重新打包独立EXE，使用新版排版请运行下述源码入口；已经生成的报告保持原样，重新核对生成的报告使用新排版。

运行环境为 Windows 10 或 Windows 11，建议使用 Python 3.11 及以上版本。正式报告交付必须安装本机 Microsoft Excel 桌面版，Python 依赖包含 pywin32；不需要 Excel 插件或启用宏。安装依赖后，直接双击 `启动银行流水核对工具.cmd`。也可以在项目目录运行：

```text
python -m pip install -r requirements.txt
python main.py
```

依赖清单已经包含桌面界面、直接读写 `.xlsx`、数据处理、内存监控和 Excel 实际验证组件；当前桌面版不读取旧 `.xls` 格式。以后再次使用时，只需双击 `启动银行流水核对工具.cmd`。需要重新生成个人独立 Windows 程序时，确认本机默认模型配置已准备好，再双击 `打包银行流水核对工具.cmd`，完成后使用 `dist\银行流水核对工具.exe`。打包脚本会显示本次构建临时目录，个人成品仅在本机交付。

### 每次核对

1. 双击 `启动银行流水核对工具.cmd` 打开当前源码版本。按当前源码重新打包后，也可以使用生成的 `银行流水核对工具.exe`。
2. 选择一份银行流水和与其对应的一份银行日记账。程序会自动分析表头位置、表头行数和列名。
3. 如有需要，可调整“跳过”和“表头行数”，再使用“自动检测”。
4. 点击“配置列映射与辅助字段”，确认日期、金额方向和文字列。
5. 在“审计策略”中按项目情况调整“实际执行重要性水平”“明显微小错报临界值”“日期容差（天）”和“组合窗口（天）”。
6. 如需调整自动确认分数门槛、组合搜索等参数，打开“高级匹配参数”；每项下方都有用途说明。
7. 如有需要，打开“大模型辅助（可选）—配置与测试”。
8. 点击“开始核对”。程序先执行十三项输入检查；业务疑点自动记录并继续，只有没有计算条件时才停止并生成独立输入问题报告。
9. 完成后，报告保存在银行流水文件所在目录，“输入检查”放在默认隐藏的浅绿色留痕区；总览直接披露范围和关键限制。本次列映射和项目记录同时保存在本机，下次读取同样表头时自动套用。
10. 打开Excel，先看“核对总览”，再查看月度、每日收支和余额差额。在“待处理事项”的黄色格选择人工结果；“对应明细”每项一行，点击“完整明细”查看原始组成和出处。“打开最近报告”允许重开已经填写保存的报告。

“生成模板”用于在所选文件夹新建两份只有标准表头的空白Excel：`银行流水导入模板.xlsx`、`银行存款序时账导入模板.xlsx`，供需要自行整理输入资料时填写。已有银行或财务系统导出文件能正常识别时，直接选择原文件即可，无需先套模板。

运行过程中，进度条和运行日志会持续显示文件读取与有效行数、十个匹配阶段、每阶段新增及累计候选数、组合搜索已处理任务数、候选选择覆盖行数、报告构造与写入节点以及各段耗时。较长步骤没有新进度时，界面仍保留当前阶段，不会把文件刚创建或生产核对结束误报为整个验收已经结束。

报告文件名格式为：

```text
银行流水名_vs_日记账名_核对报告_时间戳.xlsx
```

支持 `.xlsx`、`.xls` 和 `.csv` 文件。

## 九、列映射模式

每份文件可独立选择：

- 借贷分列；
- 单列金额加方向；
- 单列金额含正负号。

至少要正确指定日期和金额相关列。摘要可以为空，但建议选择摘要、业务说明等文字列，以提高相同金额、多笔候选时的判断质量。

## 十、最终状态

报告使用五个正式状态：

- 自动确认；
- 整组勾稽一致；
- 自动归集事项；
- 疑点事项；
- 未找到候选。

状态描述程序已经完成了什么，风险等级另行使用“正常、低风险、中风险、高风险、范围未知”。“整组勾稽一致”只确认交易组整体闭合，不声称已经找到唯一逐笔关系。因此，报告把“逐笔精确匹配率”“组级勾稽率”和“自动完成率”分开统计。

## 十一、Excel 报告与人工核对

### 业务阅读工作表（当前版本以此及开头说明为准）

| 工作表 | 查看和操作 |
| --- | --- |
| 核对总览 | 本次核了哪些记录，金额已对平多少，还需人工查看的数量、余额差额和非工作日收付提示 |
| 待处理事项 | 只列全查及抽中事项；直接呈现业务、归纳差异、具体问题，每项填写一次 |

| 每日统计 | 原有结构保留；T列写明具体差额和原因，一击直达当日证据 |
| 对应明细 | 每项一行，分别显示银行与账上收入、支出和差额；完整明细链接保留逐笔出处及整组组成 |
| 事项证据 | 每项结论、问题、双方完整组成和合计，以及已整理的其他方案；可返回黄色填写格 |
| 每日差异证据 | 每日结论、双方全部交易和对应事项归纳，直接查看整项业务 |

月度收入和支出分别比较，不能用净发生额相同掩盖两边收支差异；年月按原记录分别列示。笔数、净额和解释分项继续保留在隐藏列，可取消隐藏查看。

“对应明细”把逐笔与整组关系集中为每项一行，双方收入和支出分别列示。点击“完整明细”，直接定位到“事项证据”中的本项结论与完整组成。先列银行组成，再列序时账组成，不表示强行逐笔配对；其他备选组成的金额只在说明文字中列示，不重复计入原记录金额列。

“未对应记录”按程序初始单边结果列示。人工否定或采用其他对应后，原来在“逐笔核对”或“整组核对”中的记录仍留在原位置，并显示当前去向和结果；不会把原始分组重新搬表。整组中的各条原记录应结合“当前记录结果”查看，不能把原分组位置当作仍然有效的对应。

“核对明细”保留每条有效原记录一次，作为完整原始明细和计算依据。它与月度差异组成、原候选、人工计算及输入检查等追溯表一起默认隐藏；非工作日交易继续直接可见。原始日期、金额、账户、币种、凭证和输入映射完整保留。

普通阅读正文采用MiSans、9号字，行高贴合实际内容，大额金额显示完整。待办在前面的“程序归纳与具体问题”格集中说明结论、具体差额、入选原因及待答问题；双方记录并排，长组成可一击直达完整证据。总览不冻结，其他表只冻结首行表头。

### 人工只选择本事项的核对结果

展示表使用简短核对编号。需要人工核对的记录统一在“待处理事项”的黄色格选择结果，每项只填一次。原来的人工全查、人工抽样表放在绿色留痕区，用公式接收这个选择。已有其他对应保留在原事项的完整明细中，查看后回到黄色格选择。下拉选项及其生效规则沿用原程序：

| 结果 | 实际作用 |
| --- | --- |
| 确认对应 | 接受当前展示的双方关系，更新有效对应 |
| 确认对应并保留差额 | 接受双方属于同一业务，但原始金额差额继续保留 |
| 否定对应 | 取消原关系的有效确认，未被其他有效关系采用的原记录恢复未对应 |
| 采用其他对应N | 采用本事项下“其他对应N”展示的组成；被替代的原关系退出有效覆盖，原记录仍在原展示位置显示当前去向 |
| 保留未对应 | 人工核对后保留当前单边结果，不将其认定为已查明原因的未达账项 |

“备注”自愿填写。无需填责任人、处理日期、调整凭证或其他流程信息；不要求银行流水和序时账之外的资料。其他对应中的金额是比较说明，不重复填入原始组成金额列。填写后直接保存Excel，不需要宏、插件或将文件重新导回程序。

人工选择重复使用同一原记录时，报告提示选择冲突，冲突关系不计入有效覆盖。原始金额及期间不会因选择而变化，手续费关系公式和跨期事实也继续保留。初始程序结论与当前实际结果分开，避免把人工否定或替代后的结果仍算成原关系已确认。

### 已核对与已对平的区别

人工检查过一项业务，可以确认它存在差额或仍未对应；这属于已经作过人工核对，但不代表金额已经对平。

“当前已对平金额覆盖率”仅计算当前有效且零差额的关系，包含程序自动确认及人工确认生效的零差额关系。分别以银行侧、序时账侧原始有效交易绝对金额合计为分母，收入支出不抵销。人工确认有差额的关系不会把差额改为零，也不增加已对平金额。人工否定、重复占用冲突及被替代的无效关系退出该覆盖率。

原程序匹配率和自动确认统计保留其首次运行口径；风险分流按本次完整原始总体计算。人工结果以当前核对编号、已对平覆盖率及全查/抽样核对数量为准。自动分析结束不等于全部记录对平，未抽中和低风险留存也不等于人工确认。

### 项目历史和映射模板

- 程序保留原生成时的输入和报告指纹、列映射、参数及版本。人工填写并保存报告后，仍可以从“打开最近报告”重开；不把正常编辑视为历史失效。历史或模板保存失败时仍给出已生成报告路径。
- 列映射继续按“文件角色＋表头指纹”保存，相同表头再次导入时自动套用，并重新检查账户、币种、期间、金额方向和输入完整性。

## 十二、高级参数

日期容差和组合窗口直接在主界面“审计策略”中填写。高级设置中的参数大多数项目保持默认即可，界面会在每项下面说明用途：

| 参数 | 通俗说明 |
| --- | --- |
| 自动确认分数门槛 | 默认70、满分100；普通候选分数达标，还需业务依据充分且没有冲突或歧义，才可能自动确认，不是准确率百分比 |
| 组合最大深度 | 普通组合时，对面最多尝试合并多少笔；调大会更慢，已识别的完整业务组不受此限制 |
| 批量最少笔数 | 同日同额达到此笔数，才启动一类工资、代发汇总查找；不是所有工资分组的门槛 |
| 贪心尝试次数 | 快速补找时换顺序尝试的次数，不是把整套核对重跑多次 |
| 随机种子（-1为随机） | 固定数字便于重复查验；-1表示每次换随机顺序，不会提高业务证据的可信度；报告记录请求值和实际值 |
| 每笔最大候选数 | 控制每笔搜索保留的候选范围，越大通常越慢；普通组合目前最多取30条 |
| 内存限制（GB） | 程序内存超过此值后会减少同时处理的任务，不保证内存绝不超过该值 |
| 允许异号组合 | 允许正数和负数一起寻找组合，仍须分别核对收入、支出；专门的退款、冲正识别不受此开关影响 |
| 允许零金额匹配 | 金额确实为0的记录也可参与相关匹配；金额为空或读取失败不会按0元处理 |
| 启用贪心兜底 | 普通组合未找到结果且仍有搜索余量时，快速补找可能对应；找到后仍须检查业务依据 |
| 日期读取格式 | 按原文件的日、月、年顺序读取日期；auto表示自动识别，避免把01/02的日月读反，不用于设置报告的日期显示样式 |

两项未参与当前匹配判断的相似度输入已从界面移除。上述界面调整保留原参数默认值，没有改变匹配规则。

停止按钮会通知匹配器尽快结束。已生成的原始文件不会被改动。

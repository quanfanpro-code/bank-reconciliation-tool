# 报告排版前置单次写入

核对报告排版由"写后读回、五遍逐格修改、整体重存"改为"排版前置计算、单次写入一次成型"：新增 排版计划.py（把 make_excel 底层主题、复核报表、报告展示、紧凑报告等既有排版层逐一翻译为对内存表计划对象的同序回放）和 报告写入.py（单次写入渲染器，openpyxl 普通模式，只保存一次），reporter 默认走新路径，环境变量 银行流水核对_旧排版=1 可整体回退旧路径（旧代码原样保留，兼作逐格对比基准）。

理由：旧路径对 30 万行报告的"写入→读回→五遍排版→再存"耗时以小时计，且每遍都在已写好的文件上逐格改样式，磁盘与 openpyxl 重序列化开销占绝对大头；新路径把全部排版决策前置为纯内存计算，磁盘只碰一次。效果口径不降级：4 份真实账户金样（兴业131509、修竹010505、修竹四分610000、银座200015）新旧产物逐格属性一致（仅排除每轮必变的报告生成时间、大模型调用时间戳与耗时、输入文件哈希等元数据格）。

否决方案乙（保留读回排版、逐点消除热点）：读回再排版要经历五次完整 XML 解析与重序列化，30 万行规模下仅序列化就注定超预算，消热点只能改良常数、改不了量级。否决方案丙（大小账户双轨）：大账户出毛坯报告等于放弃大账户的排版交付质量，且两条排版路径长期必然漂移。保留 openpyxl 不换库：排版语义（主题字色、显式清框、空串重载为 None 等）全部已在 openpyxl 对象模型上逐格校准并锁进 4 份金样，换库会把这套已验证语义推倒重来，风险远大于收益；性能缺口在渲染器与计划层自身热点上消除，不靠换库。

补充（同日，口径放宽）：首版逐格复刻虽达成金样逐格一致，但 30 万行报告排版仍需约 449 秒（openpyxl 逐格样式赋值约 44 微秒/格，400 万格即数分钟），超出用户"排版不得超过计算耗时五分之一"的口径。用户明确放宽：取消一比一还原与逐格调整，排版只要"有美化、人看起来差不多"。据此加入大表快速通道：数据行超过 5 万行的表不再逐格刷样式，整列样式（列基础样式+紧凑变换按列代表值）一次落到 xlsx 列维度，数据格只写值；特例格（覆盖、后覆盖、行样式行、黄格、超链接）仍走完整逐格路径；逐行虚线边框与逐行行高取消，改表级默认行高。小表（<5 万行）保持逐格路径不变，三份小表金样逐格一致继续作为回归基准；快速通道由列级样式承接千分位、对齐、字体等主要美化。不用条件格式替代、不换库——列维度样式是 xlsx 标准能力，openpyxl 原生支持，语义已由单测锁定。


补充二（同日，直写 OpenXML）：用户进一步要求彻底摆脱 openpyxl——理由是不相信"逐格调样式"这类慢路径是必要的，且库的对象模型开销与依赖本身都不值得保留。据此写入层整体改为 直写XML.py：按表计划直接拼 styles.xml/sharedStrings.xml/各 sheet XML 并一次 zip 成型；条件格式规则由 openpyxl 对象换成自有 条件规则 结构；旧模块里被生产路径用到的纯逻辑收编进 排版共享.py，旧模块的 openpyxl 依赖改为函数内延迟导入（仅旧排版回退路径使用）。验收证据：生产导入链（排版计划/直写XML/报告写入/reporter/application）加载后 sys.modules 中无 openpyxl；排版单测 50/50 全绿（测试用 openpyxl 读回产物逐项断言）；小表金样逐格一致作为回归基准；招商 30 万行排版耗时以日志"排版耗时"计。openpyxl 只保留在测试读回和旧路径回退中。

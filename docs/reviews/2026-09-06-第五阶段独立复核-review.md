## 发现与修复

### 1. P1：指定输出路径可以覆盖原始银行流水或序时账

application.py 原来直接接受 output_path。构造 Excel 后分别用银行、账原路径及硬链接作输出，四个失败测试均证明原入口没有拒绝。现统一比较解析路径与同一文件身份，在读取匹配前拒绝；测试同时核验两份输入哈希不变。

### 2. P2：历史保存失败将已成功报告误报为任务失败

历史目录被同名文件占用、映射 JSON 损坏时，报告已经写出，后续保存异常仍抛到 GUI。现只捕获历史保存的文件/数据错误，提示未保存和报告位置；正常或失败的历史处理结束后再显示最终完成。失败样例2项，修复后真实报告可回读。

### 3. P2：同日首末行乱序导致余额误报

前日余额5000，当日文件顺序为 +300→5400、+100→5100、+200→5600，次日 +50→5650，旧实现误报4处异常。期初、连续性及期末分别依赖文件首末行，单修日内重排不足以解决。

现用每行“余额减金额→余额”的精确关系，在线性时间内检查首尾和全部关系是否连通；只在可以证明完整链时采用。没有完整证据时沿用既有容差、原行诊断。新增首日/中间日/末日、6种行序、纯收入与混合收支36项组合验证。独立复验再发现末日零净额闭环缺锚点，已新增正反行序测试并修复；期末仅在逐日连续性通过时采用累计金额提供的锚点。真实缺行仍检出，输入 DataFrame 不变。

### 4. P1：局部断档错误解除另一侧余额不足限制

银行五日余额存在可定位缺口，账仅末日有余额时，旧实现按“连续性”子串剔除原因，把“仅有1个有效余额点，连续性核对未实施”一并解除。现只对有已定位异常的同侧解除相应断档原因，其他独立限制保留。

### 5. P1：跨月多对多绕过硬边界

银行1月31日同业务 -100、-300，账2月1日 -150、-250，旧实现的 business_group 没有跨月标记；另一条已带跨月标记的完整候选也可走整组确认出口。现统一按两侧真实笔数和年月识别，并让整组出口遵守全部硬冲突条件。共同业务编号的跨月及跨年样例均保持疑点。

### 6. P1：普通跨期小额匹配没有截止性提示

银行2025年12月31日3000元服务费，账2026年1月1日同额同摘要，旧实现自动确认且截止性差异0行。旧表只取同侧退款冲销事件，与 R4 承诺不符。现独立收集所有已选跨月对应关系，列匹配ID、候选ID、双方日期、原行和金额，并保留原业务链。自动确认仍保留，截止性提示不再遗漏。

### 3. 因果定位实验（全部实测，非推断）

失败报错清一色是 Excel COM `Workbooks.Open` 失败（"Open 方法无效"）。用最小工作簿逐级加特性做二分（Excel COM 真实打开验证）：

| 最小变体 | 结果 |
|---|---|
| 裸表 / 样式 / 内外部超链接 / 批注 / 公式 / 仅筛选 / 仅 tab 色 | 全部能打开 |
| 仅冻结（`冻结="A2"`） | **打不开** |
| 旧路径（9d64c97）生成的同数据 31 表报告 | 能打开 |
| 新路径生成的同数据 31 表报告 | 打不开 |
| 修复冻结 + 摘除悬空批注声明后的同一份报告 | **能打开** |

根因：`直写XML.py:279-288` `_冻结解析` 把锚点单元格 "A2" 解析成 (列=1, 行=2)，`直写XML.py:388` 直接当作 xSplit/ySplit 写出。正确语义是"冻结行列数 = 锚点行列 − 1"（A2 应为 xSplit 省略、ySplit=1）。写出的 `<pane xSplit="1" ySplit="2" topLeftCell="A2">` 中 topLeftCell 落在冻结区左侧，违反 ECMA-376，Excel 判为需修复文件；无人值守打开（DisplayAlerts=False）直接报错。

影响面：`排版计划.py:1649` 给除"核对总览"外的每张紧凑表都设 `冻结="A2"`，即**每份报告的绝大多数表都带病**。readme 里"5 个真实账户成功打开"的说法与实测矛盾——推测当时是人工双击打开、点了 Excel 的"修复"提示，或用 WPS 打开（WPS 对该错误容忍）。交付给客户前务必用真实 Excel 验证"无修复提示直接打开"。

**修法（已验证可行）**：xSplit/ySplit 减一、为 0 时省略该属性，activePane 按"仅行冻结=bottomLeft、仅列冻结=topRight、双冻结=bottomRight"选择。同时建议修完冻结后顺带摘掉悬空批注声明（见下），双修复后的 31 表报告实测 COM 打开成功。

### 4. 为什么 752 条测试没拦住

排版单测 50 项全绿，但全部用 **openpyxl 读回**断言；openpyxl 对 pane 属性照单全收不做合法性校验，`ws.freeze_panes` 读出来还是 "A2"，断言自然通过。测试体系里唯一能发现此问题的是真实 Excel COM 打开，而那批端到端测试恰好在本次全量跑时因同一缺陷集体失败——缺陷和检测手段撞在一起，但验收记录仍写了"不新增失败"。教训：**读回验收必须包含一次"真实 Excel 能否打开"的冒烟**。

## 三、🟡 应修问题明细

**1. 批注部件悬空声明（`直写XML.py` 写簿）**
Content_Types 按"全部批注"编号声明 `comments1..N.xml`，但实际只对含批注格的表写部件；而编号时把"只有超链接没有批注"的表也计入了。实测产物声明了 `/xl/comments1.xml` 但包内没有（`xl/comments1.xml` 缺失，`comments2..8.xml` 存在）。Excel 实测容忍（仅此缺陷时能打开），但违反 OOXML 包规范，WPS/校验工具/未来 Excel 版本可能报修复。修法：编号以实际写出部件为准，或声明前先按 `批注格` 非空过滤。

**2. Decimal 格静默丢弃（`直写XML.py:229-246` vs `:259`）**
`_数字文本` 不认识 Decimal（返回 None → 该格不落盘），`_值类别` 却把 Decimal 归"数字"。金额域里 Decimal 是合法类型（`precision_engine` 全程用 Decimal），当前靠 `reporter._safe_table`（reporter.py:245-259 把 Decimal 转 float）兜底才没出事故。这是一个"类型合约不一致"的隐患：任何绕过 `_safe_table` 的新调用方都会丢数据。修法：`_数字文本` 增加 Decimal 分支（`format(v, 'f')` 或先 `%.16g` 化）。

**3. 公式格空缓存值（`直写XML.py:323`）**
写的是 `<f>…</f><v></v>`。文件头 docstring 自称"公式格 `<f>` 不带缓存值"，代码却带了空 `<v></v>`；excel-fast-writer 技能也明确要求公式不缓存值（空缓存值是"公式显示 0"类问题的常见来源）。实测 Excel 能容忍（有 fullCalcOnLoad 兜底），但应删掉空 `<v></v>` 与 docstring 对齐。

**4. 死代码崩溃点（`排版计划.py:238` → `直写XML.py:95`）**
"应用明细着色"分支会产出 `格样式(字号="")`，而 `_样式表.font` 对 `字号=""` 执行 `{号:g}` 直接 `ValueError`。已实测崩溃。该分支由 `_低置信度标记` 列触发，而全仓库无任何代码生产这个列——当前是死代码。两选一：删掉这个着色分支，或把 `字号` 归一化（空串视为 None）。倾向后者更稳。

**5. 同名输出拒绝覆盖（`排版共享.py:283-290`）**
`temporary.rename(destination)` 在 Windows 上目标已存在时抛 `FileExistsError`，GUI 用户看到的是原始异常。docstring 称是有意的"拒绝覆盖"。这不属于本次改造引入（旧路径同款），但需要您定策略：拒绝覆盖就给用户一句人话提示（"文件已存在，请换名或先关闭/移走旧文件"），或改为允许覆盖。

## 四、🟢 建议项

- `直写XML.py:734`：sharedStrings 的 `count` 与 `uniqueCount` 都填了去重数；规范里 count 应为引用总数。Excel 会自行重算，不报错，属规范偏差，顺手可修。
- `直写XML.py` 未实现 `<mergeCells>`。当前报告内容不用合并单元格（全仓 merge_cells 只出现在 input_precheck 读用户文件和测试里），暂无影响；以后若报告要标题合并，需要补这一块（含它在 sheet 子元素顺序里的固定位置：autoFilter 之后、conditionalFormatting 之前）。
- `llm_assistant.py:122` 把连续 8 位以上数字一律打码为 `***`，摘要里的长金额、8 位日期（20260115）也会被打掉。脱敏偏保守，方向对，但可能降低大模型判断质量，可视实际效果再调。
- `matcher.py:4355/4382` 等几处 `except Exception: pass` 都是并行池超时后的结果回收兜底，语义合理，可留。

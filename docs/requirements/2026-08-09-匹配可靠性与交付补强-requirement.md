# 匹配可靠性与交付补强需求

## 背景与问题

对比 `ZYQ-superman/bank-reconciliation-tool` 后，确认本程序的通用核对、预检查、风险分流和报告能力更完整，但仍有三处应补强：金额完全一致时不能绕过关键字段冲突或候选歧义；应把“摘要相同且物理连续”的整组关系纳入候选证据；仓库应提供明确的 Python 运行依赖。补强前先执行已完成的 Ponytail 冗余审计结论，避免在历史废弃链路上继续叠加功能。

## 用户与使用场景

- 用户是使用 Windows 的财务、审计人员。
- 每次运行只核对一份银行流水和与其对应的一份银行日记账。
- 原始文件只读，程序生成独立 Excel 核对报告。
- 使用者关注误配风险、复核理由、安装步骤和结果可追溯性。

## 已确认决策

1. 先清理审计确认的冗余，完成全量回归并单独提交，再开发新功能。
2. 关键账户字段明确冲突或候选存在歧义时，即使金额完全一致或差异属于明显微小范围，也必须进入“待人工复核”。
3. 新增“连续摘要整组”候选：同一侧至少两笔记录的非空摘要标准化后完全相同，且原始行号连续；整组金额、方向结构和日期窗口满足条件时，才能与另一侧单笔记录组成候选。
4. 连续摘要整组只是候选证据，必须继续经过统一评分、冲突识别、候选占用和重要性分流；不得照搬“笔数最多优先”。
5. 双方都允许形成连续摘要整组候选，但主要使用场景是多笔连续银行日记账对应一笔银行流水。
6. 交付补强采用 `requirements.txt` 和 README 安装说明；不开发 Excel VBA 版、不打包安装器，也不自动安装依赖。
7. 更新 README，完成测试、提交并正常推送到 GitHub `master`，不得强制推送。

## 功能范围

### 一、先清理冗余

- 删除未被当前报告入口调用的旧版报告生成器。
- 删除未进入正式匹配流程的旧倒排索引、旧精确/容差 worker 和旧规则执行链。
- 删除无调用者的旧结果类型和表头兼容包装。
- 将旧倒排索引测试文件改名并复用于本轮可靠性测试，不执行永久文件删除。
- 清理不得改变现有正式流程结果；以全量测试通过作为门槛。

### 二、收紧自动确认

- 在候选最终分流的共同入口增加两项强制人工复核条件：
  - `TextEvidence.conflicting_fields` 非空；
  - `MatchCandidate.is_ambiguous` 为真。
- 两项条件的优先级高于“金额完全一致”“明显微小错报”“综合可信度达标”。
- 实际执行重要性和跨月多对多等现有更严格规则继续优先生效。
- 报告必须保留明确、可读的处理原因。

### 三、连续摘要整组候选

- 复用现有 `normalize_summary`、`original_idx`、金额整数化、日期窗口、候选评分和统一选择能力。
- 摘要为空、标准化后为空、原始行号不连续、只有一笔、收支结构不一致或超出日期窗口时，不生成该候选。
- 连续组的签名金额必须与另一侧单笔记录按收入和支出分别一致，不允许正负净额抵销伪装相等。
- 新候选必须写入匹配类型、匹配阶段、组成笔数、来源侧和原始行号等证据。
- 关键字段冲突或与其他候选竞争时，仍按统一风险规则进入人工复核或被更可靠候选取代。

### 四、Python 交付补强

- 新增运行依赖清单，覆盖 GUI、表格处理、Excel 读写、`.xls` 读取和可选内存监控所需包。
- README 增加 Windows 下的安装、启动和更新依赖命令。
- 不创建 Excel 宏版本、安装程序或自动联网安装脚本。

## 明确不做

- 不开发 Excel VBA、Excel 插件或宏工作簿。
- 不增加多银行流水合并。
- 不调用外部复杂表头识别 Skill。
- 不复制对方程序的“最大笔数组优先”、同月暴力凑数或双方统一借贷方向逻辑。
- 不在本轮全面重构 `matcher.py`、`reporter.py` 或 GUI。
- 不打包 `.exe`、不发布安装器、不安装新依赖到当前电脑。

## 约束与风险

- 连续性以清洗前保留的原始行号为准，不能用清洗后的 DataFrame 索引冒充物理连续。
- 连续摘要候选可能与 DFS、批量聚合或总额候选重叠，必须由现有统一候选选择机制解决冲突。
- 自动确认规则收紧后，待人工复核数量可能增加，这是预期的风险控制结果。
- 冗余清理范围较大，但只允许删除无正式调用者的代码；任何测试失败都必须先查明调用关系。
- 依赖清单只声明依赖，不自动改变用户环境。

## 验收标准

1. 清理后现有 197 项测试全部通过，正式流程无回归。
2. 金额完全一致但关键账户字段冲突的候选，最终状态为“待人工复核”，原因说明关键字段冲突。
3. 金额完全一致但存在多个去向的歧义候选，最终状态为“待人工复核”，原因说明候选歧义。
4. 差异处于明显微小范围但存在关键字段冲突或歧义时，仍不得自动确认。
5. 两笔及以上、摘要非空且原始行号连续的同摘要记录，金额方向结构和日期窗口均满足时，能够形成“连续摘要整组”候选。
6. 原始行号有间隔、摘要为空、摘要不同、方向结构不一致或日期超窗时，不形成该候选。
7. 银行侧连续组和日记账侧连续组均有自动测试。
8. 新候选进入既有评分、候选冲突和报告链路，不新增旁路结果结构。
9. `requirements.txt` 存在，README 提供 Windows 安装和启动说明，并明确不需要 Excel 宏。
10. 全量测试、编译检查、GUI 隐藏启动、中文编码检查和端到端报告验证全部通过。
11. GitHub 云端 `master` 最终提交号与本地一致，工作区干净。

# 业务可靠性与人类友好输出需求

## 背景与问题

现有工具已经能够读取一份银行流水及其对应日记账，执行预检查、生成匹配候选并输出可追溯的 Excel 报告。但当前业务判断和报告表达仍存在三类问题：一是部分规则把金额接近、日月合计相等或程序选中提前等同于业务已经核对完成；二是明显微小错报临界值、实际执行重要性水平与候选可信度之间的职责混杂，导致一部分低风险事项被误配，另一部分本可自动处理的事项又被推给人工；三是报告把候选编号、评分拆分、大模型调用记录、JSON 等机器字段与业务结论混排，不适合作为人工直接使用的核对底稿。

本轮改造以“自动化优先、重要性分流、结果不失真”为原则：只要输入数据仍具备计算条件，程序必须自动运行到底并生成完整成果。重大、累计超限、定性高风险、歧义和影响无法量化的事项只改变风险等级、结论措辞和展示优先级，不得强制人工参与，也不得因此中断处理。

## 用户与使用场景

- 用户是使用 Windows 的财务、审计人员，不要求具备编程能力。
- 每次只核对一份银行流水和与其对应的一份银行日记账，不合并多个银行账户。
- 原始文件保持只读，程序另行生成 Excel 核对报告。
- 使用者优先需要知道核对范围是否可靠、程序自动完成了什么、剩余风险是否重大以及下一步需要处理什么。
- 技术记录必须继续保留以便追溯，但默认不干扰人工阅读。

## 已确认决策

1. 工具定位为“自动核对与异常分流工具”，而不是把所有不确定事项推给人工的候选清单工具。
2. 自动化优先：能够唯一确定、能够整组闭合或能够按重要性量化处理的事项，由程序自动完成。
3. 所有业务疑点均由程序自动形成结果。单项或累计影响超过实际执行重要性水平、明确的定性高风险、核对范围身份冲突、影响金额无法量化或无法形成可靠组级结论时，输出“高风险疑点”和建议动作，但不要求人工填写结论后才能完成。
4. 匹配关系和差异评价分开：明显微小错报临界值、实际执行重要性水平不负责证明两笔记录属于同一业务，但负责决定无法唯一落到逐笔关系的事项是否需要人工介入。
5. 多个合理答案但整个交易组在同一账户、币种、期间和方向下完全闭合时，自动认定“整组勾稽一致”，不虚构具体一一对应关系。
6. 能够量化的关键字段冲突、解析缺口或单边事项，按单项金额和累计差异池自动分流；低于阈值的事项自动归集并披露，超过阈值的事项自动列为高风险疑点。
7. 账户或币种明确不一致、同一文件混有多个账户或币种时仍生成报告，但首页必须突出显示“核对对象存在冲突，结论受限”；字段缺失时显示“核对范围身份未完全验证”。
8. 已知缺口金额按重要性水平评价；缺口金额无法计算、总体人口无法闭合时自动列为最高等级范围疑点，但程序继续处理其余可用数据并生成受限成果。
9. 允许调整报告工作表名称、顺序和可见列位置，不兼容旧报告版式；稳定匹配ID、原始行号和全部技术字段继续保留。
10. Excel 可以保留可选的人工标注列，但程序成果不依赖人工填写。用户不做任何操作时，首页和各明细也必须具有完整的系统结论、风险等级和建议动作；本轮不开发“把已复核报告重新导入程序再运行”的功能。

## 功能范围

### 一、核对范围和人口完整性

- 识别并检查可用的本方账号、币种和数据期间。
- 两侧明确身份冲突或单份文件存在混合账户、混合币种时，生成最高等级范围疑点并继续处理可用数据。
- 任一侧缺少身份字段时继续运行，但结论显示身份未完全验证。
- 汇总原始行、有效交易、排除行和解析异常行，确保每一行有去向。
- 对解析异常区分“金额可量化”和“金额不可量化”；前者进入重要性分流，后者形成最高等级范围疑点并限制结论措辞，但不停止生成报告。

### 二、自动匹配与整组勾稽

- 同账户、同币种、同期间、金额和方向一致、无关键冲突的唯一一对一关系自动确认。
- 唯一的一对多、多对一或多对多组合可以自动确认，不因笔数结构本身强制人工。
- 存在多个等额替代组合，但相关记录构成封闭交易组且收入、支出分别完全闭合时，自动标记“整组勾稽一致”。
- 日总额、月总额一致时只形成组级结论，不冒充已经建立逐笔对应关系。
- 跨期、摘要差异、对方字段冲突等风险形成结构化证据，交由重要性分流处理。
- 手续费、利息、净额结算、冲正和退汇优先形成业务类别和处理建议，不强行配成普通交易。

### 三、重要性分流

- 明显微小错报临界值用于识别可自动归集并披露的低风险事项。
- 实际执行重要性水平用于决定单项或累计事项的风险等级和展示优先级，不作为强制人工处理条件。
- 差异池继续按自然月、来源侧和收支方向分别累计，不允许跨池净额抵销。
- 多个合理答案、关键字段冲突、已知解析缺口和单边事项只要影响可量化，均进入同一分流框架。
- 单项和累计均未超过相应门槛时，程序自动归集并形成说明。
- 单项重大、累计超限或命中明确的定性高风险规则时，自动列为高风险疑点，仍由程序完成处理和输出。

### 四、余额核对

- 只有存在可靠余额数据且能够确定期初口径时才实施余额核对。
- 没有有效余额时明确显示“余额核对未实施”，不得从零推演伪余额。
- 差额为零时不得输出异常。
- 差异原因使用“发生额不一致”“余额连续性不成立”等中性事实描述，不在未经调查时定性为金额错误或时间序错误。

### 五、人类友好报告

- 首页只回答核对对象、人口完整性、自动完成结果、重大疑点和整体结论状态。
- 工作表按“结论和待办优先、业务明细其次、技术记录最后”的顺序排列。
- 疑点事项表把系统结论、说明、风险类型、处理建议及双方核心证据放在最前面，不要求人工填写后才能完成。
- 银行侧和日记账侧没有形成逐笔或组级结论的记录分别使用“银行侧待查”“日记账侧待查”，不直接认定为未达账项。
- 支出金额统一按正数展示，净额保留正负方向；金额、笔数和比例分别使用正确格式。
- 程序计算结果使用普通黑字，人工可编辑区域突出显示；非零差异按重要性显示黄或红，不按正负方向判断好坏。
- 摘要、原因和说明自动换行；JSON 辅助文字转换为“字段：内容”的普通中文。
- 候选ID、阶段、评分拆分、差异池ID、大模型调用参数和内部诊断列保留但默认隐藏。
- “运行参数”“大模型辅助明细”等纯技术工作表默认隐藏，人工可以取消隐藏查看。

### 六、自动结论与可选人工标注

- 每一项都必须由程序给出系统状态、风险等级、判断依据和建议动作，不得以“未复核”代替系统判断。
- 首页自动汇总已自动确认、整组勾稽、自动归集、低中高风险疑点的数量和金额。
- 可选人工标注只用于补充接受、调整、已处理等后续信息，不影响程序首次运行是否完成。
- 用户主动填写人工标注时，首页可以同步展示后续处理进度；用户完全不填写时，报告仍然完整可用。
- 不依赖宏和新增插件，优先使用普通 Excel 公式、数据验证和现有 openpyxl 能力。

## 明确不做

- 不合并多个银行账户或多份银行流水。
- 不开发全局最优求解器，不引入新的运行依赖。
- 不让大模型创造候选、覆盖金额规则或直接作出最终核对结论。
- 不保留一套重复的旧版工作表来兼容旧列顺序。
- 不开发已复核报告回传、多人协同系统、数据库或审批平台。
- 不开发 Excel VBA、宏、插件、安装器或新的专用环境。
- 本轮不执行 Git 提交、推送、合并或删除操作，除非用户在交付阶段另行授权。

## 约束与风险

- 重要性水平只能评价能够量化的影响；未知总体或错误账户自动形成最高等级范围疑点，但不阻止程序处理其余数据。
- 组级勾稽解决的是账户总额或业务组闭合，不代表已经找到逐笔对应关系；报告必须明确区分。
- 自动化率提高不能依赖隐藏异常或虚构配对，所有自动归集事项仍须保留原始行号和处理依据。
- 工作表名称和顺序会变化，现有报告专项测试需要同步更新。
- 可选人工标注只在当前 Excel 内生效，不承诺改变已经生成的静态单边明细布局。
- 中文文档和输出使用 UTF-8，Markdown 文档优先使用 UTF-8 with BOM。

## 验收标准

1. 金额完全一致的唯一一对一、一对多和多对一关系能够自动确认。
2. 两个以上替代组合覆盖同一封闭交易组时，形成“整组勾稽一致”，不要求人为选择虚假的逐笔关系。
3. 日总额、月总额一致只能计入组级勾稽指标，不计入逐笔精确匹配率。
4. 能够量化的歧义、字段冲突、解析缺口和单边事项按明显微小临界值、实际执行重要性水平及累计差异池自动分流。
5. 单项或累计未超限时自动归集；超过实际执行重要性水平或累计超限时自动列为高风险疑点，不强制人工参与。
6. 账户、币种明确冲突时仍自动生成受限报告并突出范围风险；身份字段缺失时生成范围未验证提示。
7. 无法量化的人口缺口不得被自动判断为不重大，但程序必须继续处理可用数据并输出最高等级范围疑点。
8. 没有可靠余额时不生成余额差异；差额为零不产生异常。
9. 支出金额在汇总、统计和明细中均以正数显示，净额符号一致。
10. 打开报告后无需横向滚动即可看到系统结论、风险等级、处理建议和可选人工标注字段。
11. 默认可见列以业务字段为主；取消隐藏后技术字段、稳定ID和原始行号完整存在。
12. 用户不填写任何人工标注时报告仍完整；用户主动填写后，首页可以同步展示后续处理进度。
13. 非零绝对差异不得因数值为正而显示为正常绿色。
14. 原文件保持不变，完整回归测试、中文编码检查和多场景 Excel 视觉复核全部通过。

## 调研摘要与来源

- 中国注册会计师协会货币资金相关审计实务资料强调同一账户、同一期间、双向核对、余额连续性、截止性以及对异常和未达事项的调查：<https://www.cicpa.org.cn/ztzl1/Professional_standards/xxzztx/zyzz/wtjd/202105/P020210507626126563401.pdf>。
- ERPNext 官方银行核对流程使用公司、银行账户、日期范围、期初和期末控制数，并区分银行交易、会计凭证、拆分结算和差异处理：<https://docs.frappe.io/erpnext/bank-reconciliation>。
- OCA `account-reconcile` 是持续维护的 ERP 级模块，可借鉴状态、交易标识和人工确认分层，但不适合直接替换本工具：<https://github.com/OCA/account-reconcile>。
- Mint 银行核对界面提供候选、拆分、内部转账、撤销和历史记录，但项目已归档且依赖 ERPNext，不适合作为本地单文件核对工具的直接基础：<https://github.com/The-Commit-Company/mint>。
- 本地代码复核范围包括 `application.py`、`data_loader.py`、`input_precheck.py`、`matcher.py`、`matching_policy.py`、`balance.py`、`reporter.py`、`make_excel.py`、`gui.py` 及现有测试。

## 待确认项

无。用户已经确认允许调整旧报告结构，并明确要求工具始终自动运行到底：业务疑点只能在结果中分级体现，不得设置必须人工参与的状态，也不得因此停止工作。

## 独立复核跟进（2026-08-29）

对《银行流水核对工具-独立复核报告》逐项复核后，追加以下验收要求：

1. 余额列存在但全部为空时，必须与“没有余额列”等同处理；不得把空值清洗成零后从零推演余额，也不得生成“余额差异明细”。
2. “匹配组成”中的交易金额统一按绝对值展示，并增加“收支方向”列；支出显示为正数，方向单独显示为“收入”或“支出”。
3. 首页除数量外，还要汇总自动确认、整组勾稽、自动归集、疑点及高风险事项的金额；建议动作按优先级至少列出三项，而不是只给一条笼统提示。
4. 可选“后续状态”仍允许完全留空；用户主动填写后，首页使用普通 Excel 公式同步显示待处理、已关注、已处理和无需处理数量。该联动不得成为程序完成条件。
5. 所有外来文字，包括原始文件的列名，写入 Excel 前都必须经过公式注入防护；程序自己生成的首页进度公式除外。
6. 影响金额为零且不存在定性风险或范围未知时，风险等级必须为“正常”，不得显示为“低风险”。
7. “输入检查”应位于业务明细之后、统计表之前；“运行参数”等技术表继续放在最后并默认隐藏。
8. 删除报告器中已经没有调用方的旧汇总和旧待处理表构造代码，更新过时注释，不保留重复实现。

复核报告提出的两项建议不纳入改造：公开的预检查回调参数继续保留以兼容既有调用方，但业务疑点不会触发该回调；两侧待查表继续保留原始业务列，技术列由现有默认隐藏规则控制，不为了减少列数而损失业务证据。

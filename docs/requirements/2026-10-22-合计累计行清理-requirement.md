# 合计、累计行清理补强需求

日期：2026年10月22日

## 背景与问题

本次核对发现，明细账的月合计、累计和最终合计标签位于“月份”列，日期及业务说明为空；最终合计行的凭证位置还填有笔数。程序原有清理主要检查日期、凭证和摘要列，没有识别这类记录，随后日期补齐会使汇总金额重复进入交易计算。

已取得的事实：明细账原始数据区域共2031行，其中19行为合计、累计记录，真实交易为2012笔。按程序现有输入检查所识别的非交易行排除后，双方各2012笔，收支合计及期初、期末余额一致。本次核对在执行适配层保留了原始行号，原始文件运行前后SHA256一致；该处理尚未写入原程序。

## 用户与使用场景

面向使用银行流水核对工具的审计人员。导入不同银行流水和银行存款序时账时，自动识别导出表中夹杂的汇总记录，避免人工逐份预先删除。

## 功能范围

1. 对银行流水和明细账统一生效，识别明确的合计、累计、小计、总计等汇总标签；标签可位于月份、日期、摘要或其他原始列。
2. 覆盖前后空白、中文或英文冒号，以及“9月合计”等带月份的常见标签。
3. 无有效日期、存在明确汇总标签的记录，即使凭证位置填有交易笔数，也不能因日期补齐变成交易。
4. 保留带正常业务内容的交易，例如“支付项目合计款”“累计结算货款”，避免仅因包含关键词就误删；正常的合并日期续行仍按原规则处理。
5. 保持当前明确汇总行排除规则；对于不能确定的记录，保留原始证据并按疑点或解析异常披露，不静默猜测或丢弃。
6. 排除发生在日期补齐和金额合计之前，保留原文件行号、原始值、排除原因，并与输入检查、数据入口处置的口径一致。
7. 更新README中的清理规则和使用说明；完成最小必要验证后提交并推送GitHub。

## 验收标准

1. 可用最小复现证明原程序会把标签位于其他列、凭证位置有笔数的汇总记录计入交易。
2. 修复后，带月份和冒号的合计、累计行在两类数据源中均被排除，不污染日期补齐和收支金额。
3. 正常交易摘要包含“合计”“累计”时仍被保留；没有汇总标签的正常日期续行仍被保留。
4. 明确汇总行、空日期异常和正常续行分别按各自规则处置，不能用汇总行规则掩盖数据错误。
5. 原始行号及排除原因可追溯，输入检查的交易数量与标准化交易数量一致。

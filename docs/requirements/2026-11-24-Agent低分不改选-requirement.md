# Agent 低分不得改选其他候选修复需求

日期：2026-11-24
状态：需求已获用户确认。

## 背景与问题

当前 `master` 起点为 `e359e43414e1762378078be7edb1f073755fe426`。独立复核发现：程序原本选择一项候选，Agent 也明确选择该项但给出较低分数时，程序会把低分写入该候选并继续参与排序，最终可能改选另一项。

已复现的结果是：没有 Agent 时选择费用所属期间为1月的记录；Agent 同样选择1月但给20分后，程序改选12月记录。两项记录的交易日期相同，1月、12月只是摘要中的费用所属期间。该行为会让低置信意见改变原本结果，并把后续核查引向 Agent 未选择的记录。

## 用户与使用场景

审计人员通过银行流水核对 Skill，让当前 Agent 根据原表文字判断同额、同日或跨日的合理候选。Agent 证据充分时可以辅助确认；证据不足或评分较低时，不应改变程序原有的候选选择和原始记录归属。

## 已确认口径

用户确认：**没有足够证据就不要改，保留原来的。**

低分答复只保留复核记录，不改变没有该答复时的候选选择。后续留存、抽查或逐项核查仍由明显微小错报临界值和实际执行重要性水平按既有规则决定，不因低分一律转为人工处理。

## 功能范围

1. Agent 答复低于自动确认门槛时，不得降低其所选候选并导致另一候选被选中。
2. 未达到确认条件的 Agent 答复不得改变原始交易归属、金额、方向、日期或现有风险分流规则。
3. Agent 证据充分且通过金额、方向、日期、关键字段冲突及候选可区分性检查时，仍可按现行规则自动确认。
4. 明确冲突、候选无法区分或其他现行拦截条件继续有效。
5. 增加能先复现改选问题的行为回归测试，并覆盖高分确认、低分不改选和冲突拦截。
6. 更新必要的使用说明和本次流程记录，完成验证后提交并推送 `master`。

## 明确不做的内容

不调整重要性水平、候选搜索范围、评分权重、报告表结构或其他匹配业务；不处理本次范围外的历史问题；不增加依赖，不派发子代理。

## 约束与风险

- 优先在现有 Agent 候选评估入口做最小修改，避免另建一套评分或选择流程。
- 修复前必须先证明测试会因实际改选而失败，修复后再证明高分确认和各类拦截未回退。
- 重要性分流仍需按原阈值执行，不能把“不改选”误写成“一律人工核查”。
- 修改已有文件前备份并校验，保留原编码和 BOM 状态；原始业务资料不写入仓库。

## 验收标准

1. 构造同日、同额且用途相近的候选，证明修复前 Agent 低分选择会把原本候选改成另一项。
2. 修复后，同一低分场景保留没有 Agent 时的候选及原始归属，不被另一项替代。
3. 低分场景的留存、抽查或逐项核查结果与既有重要性规则一致。
4. 高分且满足确认条件的场景仍能自动确认；明确冲突和无法区分的候选仍保留疑点。
5. 相关专项测试及受影响范围回归通过；记录实际命令、通过数量和既有失败，不把历史失败说成本次通过。
6. 需求、方案、计划和验收记录齐全，最终提交已推送至 GitHub `master` 并核对远端提交号。

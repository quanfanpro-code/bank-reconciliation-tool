## 一、背景与问题

本工具用于把银行流水与企业银行存款日记账自动核对，并生成 Excel 核对报告。
实务中，日记账经常把多笔银行交易合并成一笔或少量几笔记账，无法假定会计人员按银行流水逐笔登记。
本次升级的核心目标不是把大量结果重新交给人工，而是在保留审计痕迹的前提下尽可能自动处理，
只把真正高风险或重大事项留给人工复核。

项目当前已有一轮复核文档和 70 项自动测试。本轮开始时重新运行测试，结果为：

- `70 passed in 4.54s`
- 项目不是 Git 仓库。
- 现有测试通过不代表业务逻辑正确；本轮已用最小业务样例实证多项漏测问题。

### 已实证的严重问题

1. 银行流水采用“单列金额＋借/贷方向”时，程序把银行方向完全弄反：
   - 银行“贷 100 元”被处理为 `-100 元`；
   - 银行“借 40 元”被处理为 `+40 元`。
2. 日记账采用“单列金额＋方向”时，期初余额推算没有使用方向：
   - 付款 100 元、期末余额 900 元时，正确期初应为 1,000 元，程序算成 800 元。
3. 典型“一坨做账”无法日核销：
   - 银行 3 笔合计 500 元、日记账 5 笔合计 500 元，当前结果为双方 0 笔匹配。
4. 批量工资规则边界错误：
   - 代码只要求同金额记录总数超过 10 笔，却没有要求当前日期组达到 10 笔；
   - 实测可把只有 2 笔的日期组自动当作批量工资匹配。
5. 当前“高、中、低”不是统一计算的可信度百分数：
   - 有时只由日期差决定；
   - 有时只由组合笔数决定；
   - 组合匹配、日核销和月核销没有完整使用摘要等文字证据；
   - 因而现状不能可靠执行“70% 自动确认门槛”。
6. 目前只能选择一个摘要列，不能同时利用摘要、业务说明、用途、对方户名、附言和备注。
7. 当前低置信度统计按“银行行数 ÷ 匹配组数”计算，多笔组合时可能超过 100%。
8. 现有日/月总额核销的笔数差异条件与内部结构条件互相抵消，无法实现文档声称的多对多核销。
9. 金额分布分桶直接使用内部“厘”整数，却按普通金额设置边界，分布判断口径失真。
10. 大模型辅助、重要性水平分流、明显微小错报自动处理和详细待复核报告目前均不存在。

上述问题只是阶段 1 已确认的问题。阶段 4、阶段 5仍须继续执行全代码复核和回归审查，
不得把本清单当作最终缺陷上限。

## 二、用户与使用场景

### 主要用户

- 财务、会计和审计人员；
- 可能没有编程基础；
- 需要按月或一次导入全年数据进行银行流水核对。

### 典型场景

1. 银行逐笔记录，日记账按一张凭证合并多笔记录。
2. 一笔银行交易对应多笔日记账，或多笔银行交易对应一笔日记账。
3. 同一自然月内存在多对多合并记账。
4. 月末银行与次月日记账存在合理时间差。
5. 存在金额很小、无须逐笔人工处理的明显微小差异。
6. 存在超过重要性水平的大额或高风险匹配，需要人工复核。
7. 用户可选择在线大模型或本地 LM Studio，对文字语义进行辅助判断。
8. 大模型关闭、断网、超时或本地服务未启动时，基础核对仍须完整运行。

## 三、业务原则

### 3.1 自动处理优先

程序应优先完成自动核对，不能把所有低置信度项目简单丢给人工。
人工复核只处理重大、高风险、累计超限或确实无可靠结论的事项。

### 3.2 三种处理状态

所有候选结果必须明确区分：

1. **自动确认**：程序可直接采用。
2. **待人工复核**：程序已给出最可能的对应关系、评分和理由，用户只需在 Excel 中判断。
3. **未找到候选**：程序没有找到合理对应关系，继续作为未达账项。

待人工复核不得混入普通未达账项，也不得计入已确认匹配。

### 3.3 两个重要性阈值

GUI、运行参数和报告必须使用以下完整名称，不得改成简称：

1. **实际执行重要性水平**
   - 默认值：100,000 元；
   - GUI 可修改；
   - 银行侧与日记账侧分别计算绝对金额合计，取较大值作为匹配组金额；
   - 不把双方同一业务重复相加，也不使用正负抵销后的净额。
2. **明显微小错报临界值**
   - 默认值：5,000 元；
   - GUI 可修改；
   - 用于判断匹配组的金额差异是否可自动处理。

自动确认最低综合可信度默认 70%，GUI 可修改。

### 3.4 阈值优先顺序

采用更严格规则优先：

1. 匹配组绝对金额合计超过“实际执行重要性水平”时，整组进入待人工复核。
2. 未超过实际执行重要性水平，且差额不超过“明显微小错报临界值”时，
   可不受 70%可信度限制自动处理，但必须单独记录为“明显微小错报”，不得伪装成完全匹配。
3. 未超过实际执行重要性水平，且不属于明显微小错报时，
   综合可信度达到 70%才自动确认，否则进入待人工复核。

### 3.5 明显微小错报累计

明显微小错报不得跨全年无差别累计，必须同时按时间、来源和方向拆分：

- 时间：按自然月分别累计，跨月不合并；
- 来源与方向：
  1. 银行已记、企业未记——收入；
  2. 银行已记、企业未记——支出；
  3. 企业已记、银行未记——收入；
  4. 企业已记、银行未记——支出。

收入与支出不得相互抵销。

每个自然月、每个差异池的累计绝对差额与“实际执行重要性水平”比较。
累计超过实际执行重要性水平时，不要求用户逐笔复核；
整个池汇总成一项“月度累计超出实际执行重要性水平”的待复核事项，
并在报告中附全部组成明细。

### 3.6 完全匹配与自动处理分开披露

报告必须同时披露：

- 精确匹配率：金额真正完全对上的结果；
- 自动处理率：包含明显微小错报自动处理后的结果。

明显微小错报必须保留双方金额、差额、所属月份、差异池、累计值和处理依据。

## 四、匹配业务规则

### 4.1 金额方向

1. 银行流水：
   - 贷方、收入、收、入账为增加，金额为正；
   - 借方、支出、付、出账为减少，金额为负。
2. 企业日记账：
   - 借方为银行存款增加，金额为正；
   - 贷方为银行存款减少，金额为负。
3. 借贷分列、单列金额＋方向、已含正负号三种模式必须分别测试。
4. 未识别方向不得静默猜测，必须记录解析异常并排除该行。

### 4.2 一对一与多对多

1. 普通一对一交易可在日期容差内跨月匹配，兼容月末付款、次月银行入账。
2. 多对多“一坨做账”只在同一自然月内自动组合。
3. 跨月多对多候选进入待人工复核。
4. 日核销、月核销必须真正支持双方笔数不同，不能被内部条件变相限制为笔数相同。
5. 多对多报告按“匹配组”展示，不得用任意逐行对齐制造虚假的一一对应关系。

### 4.3 多个辅助文字字段

GUI 从“单个摘要列”升级为“可选择多个匹配辅助列”。

默认自动勾选名称中含以下词语的列：

- 摘要；
- 业务说明；
- 交易用途；
- 对方户名；
- 附言；
- 备注。

账号、卡号、凭证号和其他列默认不勾选。
凭证号不作为核心匹配依据。

程序应综合使用用户选择的多个字段，而不是只做单一正则匹配。
基础文字能力至少包含关键词、规范化、字面相似度、字段一致性和冲突检查。

### 4.4 综合可信度

必须建立统一的 0～100 综合可信度，至少体现：

- 金额关系；
- 日期距离；
- 多字段文字相似度；
- 对方信息一致性；
- 规则命中情况；
- 组合笔数与组合复杂度；
- 是否跨月；
- 是否存在相互矛盾的证据；
- 可选的大模型语义评分。

具体权重、封顶规则和硬性否决条件在阶段 2 方案设计中确定。
无论采用何种权重，金额、方向、重要性水平和累计规则均由程序确定，
不得交给大模型计算或覆盖。

## 五、大模型辅助匹配

### 5.1 定位

大模型是可选增强项，不是程序运行的必要条件。
它只处理基础规则筛选出的少量含糊候选，负责理解摘要和业务说明等文字语义。
大模型只能从给定候选中选择和评分，不能凭空创造候选，也不能单独决定最终状态。

### 5.2 支持方式

GUI 至少提供：

- 是否启用大模型辅助；
- 在线 API或本地 LM Studio；
- 接口地址；
- 模型名称；
- API 密钥；
- 超时时间；
- 每次提交的候选数量；
- 连接测试。

优先采用 OpenAI 兼容接口，使在线服务与 LM Studio 共用同一套调用层。

### 5.3 API 密钥

- 输入框必须隐藏显示；
- 密钥只在本次运行期间保留；
- 关闭程序后不得写入普通配置文件；
- 可从 Windows 环境变量读取；
- 不得进入日志、报告、错误信息或原始模型记录。

### 5.4 数据保密

在线 API 默认只发送当前候选组必要的日期、金额、摘要和业务说明：

- 不发送整份流水；
- 不发送源文件路径；
- 不发送银行账号和卡号；
- 账号等敏感字段在本机比较，只发送“相同/不同”的结果。

本地 LM Studio 可使用用户明确勾选的全部辅助字段。
GUI 必须清楚显示在线模式将发送哪些字段。

### 5.5 失败降级

发生断网、超时、限流、接口错误、本地服务未启动、模型不存在或返回格式错误时：

- 不得中断整次核对；
- 自动退回基础文字相似度和规则评分；
- 按相同的重要性与可信度规则继续分流；
- 在报告中记录失败原因、降级次数和受影响匹配组。

### 5.6 返回验证与可追溯

大模型应返回固定结构，至少包括：

- 选择的候选编号；
- 语义评分；
- 判断理由；
- 支持证据；
- 冲突证据；
- 不确定性；
- 建议状态。

程序必须重新验证候选编号、金额、方向、日期和所有阈值。
清理敏感信息后的模型原始回答完整保留在报告中。

## 六、Excel 报告

### 6.1 待人工复核

新增独立“待人工复核”Sheet，至少包含：

- 匹配组编号和处理原因；
- 双方原始文件行号；
- 日期、金额和辅助文字字段；
- 匹配组绝对金额合计；
- 金额差异；
- 综合可信度及分项评分；
- 命中的重要性规则；
- 大模型判断和理由（如有）；
- 月度累计池及累计值（如适用）；
- “复核结论”下拉项：接受、拒绝、暂不处理；
- “复核说明”空白填写列。

默认复核结论为“暂不处理”。
人工复核在 Excel 中完成，不在 GUI 中制作复杂复核表。

### 6.2 大模型辅助明细

启用或尝试调用大模型时，新增“大模型辅助明细”Sheet，逐组记录：

- 调用编号、时间、接口类型、接口地址的非敏感部分、模型名称；
- 候选组和原始行号；
- 实际发送字段；
- 本地规则分项评分；
- 模型选择、语义评分、理由、支持证据、冲突证据和不确定性；
- 最终综合可信度；
- 最终状态及采用的阈值；
- 调用成功、失败或降级状态；
- 耗时和接口返回的用量统计；
- 清理敏感信息后的原始回答。

### 6.3 汇总与明细

“核对汇总”至少增加：

- 精确匹配率；
- 自动处理率；
- 自动确认组数；
- 明显微小错报组数与金额；
- 待人工复核组数与金额；
- 未找到候选笔数与金额；
- 各自然月、各差异池累计情况；
- 大模型是否启用、成功/失败/降级次数、参与判断组数和状态变化数。

所有多对多匹配按组展示汇总和组成明细，不得用随意逐行并排暗示不存在的一一对应关系。

## 七、GUI 要求

GUI 必须按 `desktop-gui-style` 规范整体审查和优化，而不是零散增加控件。

### 视觉模块

1. 页眉与简短说明；
2. 输入文件；
3. 核心核对参数；
4. 列映射与多个辅助字段；

### 验收重点

- 界面美观大方，亮色和暗色主题均可用；
- 输入、参数、辅助字段和大模型配置层级清楚；
- 两个重要性阈值使用完整名称；
- 同类输入框和按钮对齐、尺寸一致；
- 主按钮明显强于普通按钮；
- 新增配置不得把日志区压缩到难以使用；
- 窗口缩放后不出现控件重叠、遮挡或无法访问；
- 大模型关闭时，相关配置不干扰普通用户；
- 错误提示使用普通用户能理解的语言。

- 不让大模型直接计算金额、方向、阈值或累计值；
- 不让在线接口接收整份流水或未明确授权的敏感字段；
- 不把大模型作为必需依赖；

- 不执行 Git 提交、推送、建分支或其他 Git 写操作；
- 不修改原始银行流水和日记账文件。

## 九、约束与风险

- 目标平台仅为 Windows；
- 项目现有技术为 Python、pandas、openpyxl、CustomTkinter；
- 现有 70 项测试必须保持通过；
- 所有新增核心行为必须先写失败测试，再实现；
- 修改前已创建项目外完整备份；
- 多对多匹配会提高自动处理率，也会增加错配风险，必须由统一评分、重要性水平和详细报告共同控制；
- 本地小模型可能不支持严格结构化输出，必须有格式校验、有限重试和自动降级；
- 在线接口存在费用、限流、隐私和网络风险，必须默认关闭；
- 现有报告结构较笼统，需要避免为了“信息详细”而重复堆砌相同字段。

## 十、验收标准

1. 现有 70 项测试全部通过，新增测试覆盖正常、边界和错误路径。
2. 银行“贷增借减”和日记账“借增贷减”在三种金额模式下均正确。
3. 银行单列“贷 100、借 40”分别得到 `+100、-40`。
4. 日记账单列方向参与期初余额推算，付款 100、余额 900 时期初为 1,000。
5. 银行 3 笔与日记账 5 笔同月合计相等时，多对多逻辑可以生成一个匹配组。
6. 批量工资仅在当前日期组达到规定最小笔数且双方摘要条件成立时自动匹配。
7. “实际执行重要性水平”默认 100,000 元、“明显微小错报临界值”默认 5,000 元、
   自动确认最低综合可信度默认 70%，三者均可在 GUI 修改并写入报告；
   匹配组金额按双方绝对金额合计的较大值计算。
8. 阈值冲突时采用更严格规则，测试覆盖“大额但差额很小”的情况。
9. 明显微小错报按自然月和四个差异池分别累计，收入支出不抵销。
10. 单个月度差异池累计超过实际执行重要性水平时，生成一项整池待复核事项并附组成明细。
11. 同月多对多可自动组合；跨月多对多只能进入待人工复核；普通一对一仍可按日期容差跨月匹配。
12. GUI 可分别为银行和日记账选择多个辅助文字列，并按确认的字段名规则自动勾选。
13. 综合可信度为 0～100，报告能展示主要分项和最终分流理由。
14. 大模型默认关闭；关闭时基础核对完整可用。
15. 在线 OpenAI 兼容接口和本地 LM Studio 均可配置；可获取模型列表或测试连接。
16. 使用模拟接口验证大模型成功、超时、断网、非法候选、错误格式和自动降级，不使用真实流水做网络测试。
17. API 密钥不落盘、不进入日志和报告。
18. 在线模式不发送整份流水、文件路径、账号和未勾选字段。

## 十二、已确认事项

- 自动处理优先，不采用“全部低置信度都人工复核”；
- 两个重要性阈值的正式名称、默认值和 GUI 可调；
- 匹配组金额按绝对金额合计；
- 明显微小错报可自动处理但必须单独披露；

- 精确匹配率与自动处理率分开；

# 余额断档局部降级需求（2026-09-06）

## 背景与问题

真实数据验证（东方农博民生银行，银行流水 2,509 行对序时账 2,633 行）暴露：流水在两个月份交界缺行（2025-07-01 断档 -499,558.37；2026-07-01 断档 +316,072.25），总体余额控制不闭合。现行机制把"余额控制不闭合"作为结构性问题触发全局范围受限：`matcher.py:1621` 给每个候选盖 `overall_scope_limited` 戳，`matching_policy.py:392` 据此把所有匹配一律降为疑点、范围未知。结果 2,264 笔总差额为 0 的精确匹配被连坐降级，疑点表多达 2,354 行。用户明确指出该机制不对（"数据缺一行、全场陪绑，不补缺口也不能这样"），要求修复。

## 用户与使用场景

注册会计师用本工具核对单账户银行流水与银行存款序时账。断档多源于银行或导账工具漏导月份交界记录，属常见数据瑕疵，不应使整份核对失去自动确认价值。

## 功能范围

1. 余额连续性断档能定位到具体日期时，仅"断档窗口"涉及的匹配关系降为疑点、范围未知；窗口外的匹配按原有证据规则正常自动确认、整组勾稽。
2. 断档窗口口径（用户已确认）：断档日＋前一个有余额记录的交易日，含两日全天。缺行只可能落在两个余额锚点之间。
3. 匹配关系任一侧（银行或序时账）记录日期落在窗口内，即视为涉及该窗口。
4. 系统结论与核对结论表改为披露断档日期、差额和受影响区间，不再笼统写"总体余额控制异常、相关关系全部降为疑点"。
5. 待查记录处理不变；"余额连续性异常"表照常披露断档。

## 明确不做的内容

- 其他结构性原因（期间或收支无法计算、账户/币种/金额口径未验证、存在解析异常排除行）维持整体降级不变。
- 断档无法定位到日期（无余额列、余额不可解析），或断档窗口合计覆盖超过半数有记录交易日（余额链名存实亡）时，回退为整体降级。
- 不改动组合搜索预算与匹配算法本身。

## 约束与风险

- 审计依据：窗口外每一天都有余额锚点，记录完整性被日界勾稽证明；窗口内保守降级可辩护。
- 残余风险：窗口划定偏窄漏掉受影响记录——由"缺行只可能落在两个余额锚点之间"控制。
- 与既有测试冲突：多个测试断言整体降级（如 test_第二阶段终审范围与规模、test_阶段一终审硬闸门与报告），需同步更新预期。

## 验收标准

1. 构造样本：断档在某日，窗口内匹配降级、窗口外零差额匹配正常自动确认。
2. 构造样本：断档无法定位（或窗口覆盖过半）时回退整体降级。
3. 真实数据（东方农博民生银行）重跑：不触及 2025-06-29~07-01、2026-06-29~07-01 两个窗口的零差额匹配恢复自动确认；系统结论列明断档位置与受影响区间；余额连续性异常表仍为 2 处断档。
4. 全量测试通过；readme 更新日志与设计文档第 46 条同步更新。

## 待确认项

无。窗口内记录只降级、窗口口径为"断档日＋前一有记录交易日"两项决策已经用户确认。

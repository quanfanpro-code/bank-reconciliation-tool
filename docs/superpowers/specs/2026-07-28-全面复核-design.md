# 银行流水核对工具 v3.0 全面复核 — 方案设计

日期：2026-07-28
对应需求：docs/requirements/2026-07-28-全面复核-requirement.md

## 一、方案比较

### 方案 A：定点修复 + 测试加固

对需求文档中 P0/P1/P2 清单逐项最小修复，每项配回归测试。
- 成本：低；风险：低；可逆性：高。
- 缺点：`extract_initial_balance` 这类「猜列名 + 裸 Decimal」是模式性缺陷，
  只修单点会留下同类隐患（例如换了列名又复发）。

### 方案 B（推荐）：定点修复为主，两处模式性收口

在 A 的基础上做两处有边界的收口，其余一律不动：
1. **期初余额提取改为 mapping 感知 + 统一金额解析**：
   `extract_initial_balance(df, mapping=None)` 新增可选 mapping 参数
   （Reporter 传入用户已校验的列映射），所有余额/金额取值改走
   `clean_amount` 容错解析，解析失败回退为「无法确定（0 并不再报警为差异）」语义。
2. **空值语义统一**：金额/余额单元格「缺失」一律为 None，「真 0」才是 0.00；
   下游（期初推断、每日统计、连续性检查）按 None=缺失处理。
- 成本：中；风险：中（std_balance 语义变更影响下游，需全链路回归）；收益：消灭一类 bug。

### 方案 C：模块边界重构

重写 data_loader/balance/reporter 的协作边界。
- 拒绝：过度工程，超出本次需求范围，回归风险不可控。

## 二、推荐方案的逐项设计

### P0-1 默认参数无法启动（validate.py / gui.py）

- `validate.py` 上限调整为：组合窗口 ≤ 90、最大深度 ≤ 100、最大候选数 ≤ 200（不变）、
  日期容差 ≤ 365（不变）。上限仍存在（防组合爆炸的初衷不变），但不再误伤文档默认值。
- 随机种子允许 -1（readme 文档化语义），其余负值仍拒绝。
- GUI「允许异号」默认改为不勾选（对齐 readme）。
- 数据流：GUI 输入 → validate → MatcherConfig，不变。

### P0-2 批量聚合 category 崩溃（matcher.py）

- `match_batch_aggregation` 中 `group['summary'].fillna('')` 改为
  `group['summary'].astype(str)` 前先做空值处理：用
  `group['summary'].map(lambda s: '' if pd.isna(s) else str(s)).str.lower()`，
  规避 category fillna 限制，行为等价。
- 顺带排查全项目对 category 列的 fillna 调用（仅此一处）。

### P0-3 / P1-5 期初余额提取（balance.py / reporter.py）

- 签名扩展：`extract_initial_balance(df, mapping=None)`。
  mapping 提供 date/summary/balance/debit/credit/amount 列名时优先使用；
  不提供时保留现有自动探测作为兜底。
- 所有取值改走 `clean_amount`；解析不出来的行跳过而非崩溃。
- 无任何可用余额信息时返回 `Decimal('0')` 并新增返回值约定说明（保持现有返回类型，
  Reporter 端以「双方是否都有余额数据」决定是否发警告——见下）。
- Reporter：银行和日记账两侧分别判断「是否存在有效余额列数据」，
  仅当两侧都有余额数据且期初差 > 0.01 时才发期初不一致警告；
  任一侧无余额数据时不发警告并在汇总表注明「未提供余额列，跳过期初核对」。

### P1-4 空余额单元格语义（data_loader.py）

- `std_balance`：原始单元格为缺失 → None；解析失败 → None 并记录；
  有值 → Decimal。
- 下游回归点：`balance.extract_initial_balance`（dropna 后取数）、
  `reporter.calculate_daily_stats`（`notna().any()` 判断 has_bal，语义反而变准）、
  `check_balance_continuity`（新增调用，见 P1-8）。

### P1-8 余额连续性异常 sheet（reporter.py）

- `generate_report` 中调用 `check_balance_continuity`，分别对银行/日记账标准化数据
  （含有效 balance 时）生成异常记录，合并为一个「余额连续性异常」sheet。
- 无余额数据时不生成该 sheet（与现有「空 df 跳过」机制一致）。

### P1-9 汇总表数字类型（reporter.py）

- 去掉 `df_sum.astype(str)`；数值项保留 int/float，文本项保持 str，
  让 Excel 中可计算。（readme 的 P1 修复记录由此落到实处。）

### P1-10 报告确定性（reporter.py）

- 匹配明细的 `all_ids` 排序键：每个 match_id 取该组（银行侧最早日期, 银行侧金额, id），
  排序后遍历，保证同数据同参数两次运行行序一致。

### P2 组（低风险顺手修）

- P2-11：readme 同步描述（严格结构校验），代码不动。
- P2-12：`match_exact_1to1` 并行异常改记 `exception_logger`（与其余阶段一致）。
- P2-13：`_randomized_greedy` 修正为「shuffle 后不再全局 sort」，
  排序仅作为 attempt 0 的确定性基线。
- P2-14：`standardize_data` 在 `single_amount_with_direction` 且方向列缺失时，
  全部金额记录为解析失败（不再静默按正数）。
- P2-15：`round_decimal` 的 Decimal 路径尊重 `decimals` 参数。
- P2-16：`_postprocess_summary` 涂色范围改为数据行 2..7（跳过表头）。
- P2-18：删除死参数/死 import/死函数（`load_file(chunksize)` 参数保留签名但标注未用，
  避免破坏 GUI 调用；`_greedy_fallback` 删除；清理死 import）。

### 不做

- `_match_total` 严格校验保持现状（A3 假设：代码比 readme 严，改 readme）。
- 匹配算法策略、模块结构、公开 API 签名（除 `extract_initial_balance` 新增可选参数）不变。

## 三、数据流与错误处理

- 数据流不变：load_file → standardize_data → Matcher → Reporter → make_excel。
- 错误处理原则：解析层「容错+记录」（现有 ParseErrorCollector 机制扩展到期初提取）；
  匹配层「异常入 exception_logger」（补齐精确匹配阶段）；报告层「缺数据则跳过对应 sheet」。
- std_balance 语义变更是唯一的行为变更点，回归面：
  extract_initial_balance / calculate_daily_stats / check_balance_continuity / 运行参数表，全部有测试覆盖。

## 四、测试策略

- 每个 P0/P1 修复先写失败测试（RED），再最小实现（GREEN），再全量回归（VERIFY）。
- 测试文件：新增 `tests/test_review_fixes.py`，不改动既有 46 个测试的行为预期
  （唯一例外：validate 上限调整后，既有测试用值 30/20 仍在新上限内，不受影响）。
- 关键用例：category summary 聚合不崩溃且匹配正确；千分位余额期初提取不崩溃且数值正确；
  空余额→None；期初推断跳过空余额单元格；默认参数通过校验；种子 -1 通过校验；
  汇总表数值单元格为数字类型；匹配明细两次运行行序一致。

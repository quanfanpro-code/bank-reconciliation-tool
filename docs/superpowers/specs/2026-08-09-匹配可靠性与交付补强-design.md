# 匹配可靠性与交付补强设计

## 目标

先删除已确认不在正式调用链中的历史实现，再用现有候选、评分、分流和报告结构补强三项能力：冲突与歧义强制复核、连续摘要整组候选、Python 依赖声明。所有改动保持一份银行流水对应一份银行日记账，不引入 Excel 宏或新的运行依赖。

## 方案比较

### 方案 A：复用现有统一候选管线（采用）

- 在 `route_candidate` 的共同分流入口增加风险硬门槛。
- 在 `Matcher` 中增加一个连续摘要整组候选阶段，复用 `normalize_summary`、`original_idx`、`_total_structure_matches`、`_add_candidate` 和现有日期窗口。
- 新增 `requirements.txt`，README 只说明标准 Python 安装和启动方式。
- 优点：改动集中、结果结构不变、可用现有报告和测试链验证。
- 风险：新候选会与 DFS 或总额候选竞争，但统一候选选择已经负责排除重复占用。

### 方案 B：建立可配置的连续片段匹配引擎（不采用）

- 支持摘要容差、允许间隔行、最小/最大组长度和独立 UI 参数。
- 优点：适配面广。
- 缺点：把一个明确业务特征扩张成新框架，增加参数、误配面和测试成本，不符合 Ponytail 最小实现原则。

### 方案 C：只在报告中提示连续摘要组（不采用）

- 不生成匹配候选，只把连续组列为人工提示。
- 优点：风险最低。
- 缺点：不能改善现有组合候选排序，也无法利用已存在的统一评分与分流能力。

## 分流规则设计

最终分流顺序保持“更严格规则优先”：

1. 匹配组金额超过实际执行重要性水平；
2. 跨月多对多；
3. 关键字段冲突；
4. 候选歧义；
5. 金额完全一致；
6. 差异不超过明显微小错报临界值；
7. 综合可信度达到门槛；
8. 其他候选进入人工复核。

关键字段冲突和候选歧义可以同时存在，处理原因合并展示，避免只暴露其中一项。它们必须挡住“金额完全一致”和“明显微小”两条自动确认路径。

## 连续摘要整组设计

### 组的识别

- 按 `original_idx` 排序，而不是按清洗后的 DataFrame 索引。
- 摘要通过现有 `normalize_summary` 标准化。
- 标准化摘要非空、相邻原始行号差为 1、组内摘要键完全相同，才属于同一连续组。
- 组至少两笔；原始行号缺失时不推断连续性。

### 候选生成

- 先扫描日记账连续组，对银行侧单笔生成候选；再对称扫描银行侧连续组，对日记账单笔生成候选。
- 连续组签名金额与目标单笔金额必须相同。
- 使用 `_total_structure_matches` 分别检查收入和支出结构，禁止正负抵销。
- 组内与目标记录的最大日期跨度不得超过 `dfs_date_window`。
- 金额为零时沿用 `allow_zero_match` 规则。
- 生成 `continuous_summary_group` 候选，记录来源侧、标准化摘要、组成笔数和原始行号。
- 设置结构规则证据，但不设置“无歧义整组”特权；与其他候选竞争时仍由全量候选判断歧义并统一排序。

### 数据流

```text
标准化数据
  → 原始行号连续组识别
  → 金额、收支结构、日期窗口筛选
  → _add_candidate
  → 统一文字评分与关键字段冲突识别
  → 全量候选歧义识别
  → 非冲突候选选择
  → route_candidate 风险分流
  → 现有 Excel 报告
```

## Python 交付设计

新增一个运行时 `requirements.txt`，声明 `customtkinter`、`numpy`、`openpyxl`、`pandas`、`psutil` 和 `xlrd`。README 提供 Windows 下创建环境、安装依赖、启动程序的最短命令。`psutil` 虽在代码中可以缺省，但纳入依赖后能稳定启用内存降级保护；`xlrd` 用于 README 已承诺支持的 `.xls` 文件。

不新增开发依赖清单、批处理安装器、Excel 宏或打包工具。用户仍通过 Windows 文件选择窗口选择输入文件。

## 错误处理

- 连续组缺少原始行号或有效摘要时静默跳过，不把普通数据问题升级为程序错误。
- 日期或金额数据已在输入预检查被阻止；匹配阶段仍只接受标准化后的有效数据。
- 关键字段冲突和歧义不是运行错误，写入“待人工复核”及处理原因。
- 依赖缺失由 Python 的标准导入错误暴露，README 给出统一安装命令，不编写第二套自定义依赖检查器。

## 测试策略

1. 清理前以当前全量测试为基线，清理后运行剩余回归测试。
2. 分流测试覆盖：完全一致冲突、明显微小冲突、完全一致歧义、冲突与歧义并存、无风险完全一致。
3. 连续组测试覆盖：日记账多笔对银行单笔、银行多笔对日记账单笔、行号间隔、空摘要、摘要不同、混合方向和日期超窗。
4. 管线测试确认连续候选能够进入统一选择并在报告中展示。
5. 最终运行全量测试、编译检查、GUI 隐藏启动、中文编码扫描和端到端报告验证。

# 银行流水核对输入预检查——方案设计

日期：2026-08-08  
对应需求：`docs/requirements/2026-08-08-输入预检查-requirement.md`

## 一、设计目标

本次优化在现有核对流程前增加一层自包含的输入预检查，同时保留现有匹配算法和报告口径。设计重点是：

1. 一次只处理一份银行流水和与其对应的一份银行日记账；
2. 文件选择后自动识别表头，点击“开始核对”后先检查、再匹配；
3. 表头识别同时利用位置、非空分布、数据类型转换、关键词、合并单元格和相邻行关系；
4. 硬错误阻止运行，普通提示由用户决定是否继续；
5. 无图形界面的调用入口执行同一套硬性检查；
6. 最终 Excel 保留“输入预检查”工作表；
7. 不新增第三方依赖，不调用外部 Skill，不修改原始文件。

## 二、方案比较

### 方案 A：只在现有流程中追加若干判断

做法：继续使用当前“命中两个关键词即认定表头”的方法，在 `application.py` 中直接增加日期、金额和非空率判断。

优点：改动代码最少。

缺点：不能可靠支持多行或合并表头；界面、无界面入口和报告容易各写一套判断；结构歧义无法表达；以后新增检查时会继续堆积条件分支。

结论：不采用。它无法满足本次最关键的表格结构验收标准。

### 方案 B：增加自包含的结构识别与预检查模块（采用）

做法：

- `DataLoader` 继续负责文件读取和标准化；
- 新增小型 `input_precheck.py`，集中保存结构候选、检查项、分级结果和报告转换；
- `DataLoader` 的自动表头检测改为调用本地确定性结构识别，并支持一至三行表头；
- `application.run_reconciliation` 在匹配器创建前统一执行预检查；
- GUI 只负责展示阻止事项或普通提示，不复制业务判断；
- `Reporter` 直接接收同一份预检查结果并写入 Excel。

优点：一套规则同时服务自动读列、正式运行、无界面入口和报告；复杂表头原则被固化为普通代码；现有读取、清洗、列映射、异常收集器和报告流程可以继续复用。

缺点：需要调整读取函数的表头层级参数，并为 GUI 增加“表头行数”状态。

结论：采用。它是满足验收标准所需的最小完整边界。

### 方案 C：建设通用复杂表格识别引擎

做法：扩展到多工作表、PDF、图片、网页、跨页续表、嵌套表和左右并列表。

优点：通用性强。

缺点：远超银行流水核对的实际需要，测试面和维护成本显著增加，也违反本次明确排除范围。

结论：不采用。

## 三、整体流程

```text
选择单个文件
  → 扫描前部表格结构
  → 给出跳过行数、表头行数、派生列名和候选证据
  → 用户检查或调整列映射
  → 点击开始核对
  → 读取双方文件并执行八项预检查
      → 有阻止事项：返回调整
      → 有普通提示：用户选择继续或返回
      → 无异常：直接继续
  → 运行现有匹配器
  → 报告写入“输入预检查”工作表
```

预检查不改写输入文件，也不把金额差额当作输入错误。差额只作为核对前的事实展示。

## 四、表格结构识别

### 4.1 扫描范围

- 扫描活动工作表或 CSV 的前 40 行；
- 评估一至三行连续表头候选；
- `.xlsx` 使用项目已经依赖的 `openpyxl` 读取合并区域；
- `.xls` 和 `.csv` 使用现有 `pandas` 读取能力，不增加依赖。

### 4.2 候选证据

每个候选同时计算：

- 表头区域非空单元格数量和横向覆盖率；
- 文字单元格比例及列名重复程度；
- 日期、金额、借贷、方向、摘要、余额等业务词支持；
- 候选下方数据行的非空分布是否稳定；
- 从表头到数据区是否出现日期/数字类型转换；
- 合并单元格是否与候选区域相交；
- 是否像只有一两个单元格的标题、单位或注释行。

关键词只是证据之一，不能单独决定表头。候选按综合证据排序，并保留次优候选用于歧义判断。

### 4.3 多行表头与派生列名

- 合并区域的左上角文字沿合并范围传播，仅用于推导结构；
- 多行表头按列收集由上到下的非空文字，去除连续重复后用稳定分隔符连接；
- 空表头使用稳定的“第 N 列”名称；
- 重复列名按出现顺序追加序号；
- 原始单元格内容不修改，派生列名只用于读取和列映射。

### 4.4 歧义处理

当两个候选分数接近且会产生不同表头范围时，结果标记为歧义：

- 如果歧义会使当前必填映射失效，列为阻止事项；
- 如果用户采用的表头仍能形成完整有效映射，列为普通提示并要求确认；
- 不在日志中静默选择后直接进入匹配。

## 五、预检查模型

`input_precheck.py` 使用三个简单数据对象：

- `TableStructure`：采用的跳过行数、表头行数、派生列名、得分、候选和歧义；
- `PrecheckItem`：检查项目、双方结果、比较结果、状态和说明；
- `InputPrecheckReport`：全部检查项，并提供阻止事项、普通提示、弹窗摘要和 Excel 表格转换。

状态统一为：

- `通过`：可以继续；
- `提示`：集中展示后可以继续；
- `阻止`：不得启动匹配。

不为每项检查建立独立类，也不引入插件或配置框架。

## 六、八项检查的确定规则

### 6.1 文件读取

文件必须存在、为普通文件、后缀为 `.xlsx`、`.xls` 或 `.csv`，能成功读取且至少有一行可核对数据。失败即阻止。

### 6.2 表格结构

记录实际采用的表头位置、层级、派生列名、首选候选和歧义。不能形成列名或重大歧义影响必填映射时阻止；用户设置与首选候选不同但映射仍有效时提示。

### 6.3 日期范围

标准化后分别计算最早和最晚日期。全部失败时阻止；少量失败或双方范围不同只提示。

### 6.4 金额方向

继续复用现有方向解析：银行流水贷方/贷/收入为正、借方/借/支出为负；银行日记账相反。方向模式中存在无法识别且对应金额有效的方向值时阻止，避免把收入支出颠倒。

### 6.5 金额合计

标准化后按正负分别计算收入合计和支出绝对值合计，展示银行流水、银行日记账及两项差额。任一侧金额全部失败时阻止；部分失败或合计有差额只提示。

### 6.6 非交易行

识别并统计：全空行、合计/累计/统计行、重复表头、单格标题和注释行。预检查披露数量，正式匹配继续依靠日期和金额有效性及现有汇总行规则排除这些记录。发现并排除时提示，不直接阻止。

### 6.7 必填字段

所有模式都要求日期列；借贷分列要求借方和贷方列；单列金额加方向要求金额和方向列；带正负金额要求金额列。缺失、重复或不在实际列中时阻止。

### 6.8 辅助文字完整性

对摘要和用户选择的辅助文字列去重后逐列计算非空率。低于 80% 或未选择可用文字列时提示；数据充分时通过。该结果只影响核对前提示，不改变现有匹配评分。

## 七、界面与无界面入口

### 7.1 GUI

- 选择文件后自动分析，不新增预检查按钮；
- 输入卡片增加“表头行数”，自动检测同时填写“跳过”和“表头行数”；
- 后台线程得到阻止结果后，在主线程弹出错误说明；
- 普通提示使用一次汇总确认框，按钮含义为“继续核对”和“返回调整”；
- 用户返回调整时按正常取消处理，不生成报告。

### 7.2 `run_reconciliation`

- 默认自动识别表头；显式传入跳过行数或表头行数时尊重调用方设置；
- 硬错误始终抛出带完整报告的 `InputPrecheckBlockedError`；
- 无界面调用遇到普通提示默认记录后继续；
- GUI 可传入普通提示确认回调，但预检查规则仍只实现一次。

## 八、报告集成

`Reporter` 新增可选的 `precheck_report` 参数。`build_report_tables` 在现有工作表之外加入“输入预检查”，列固定为：

- 检查项目；
- 银行流水结果；
- 银行日记账结果；
- 双方比较结果；
- 状态；
- 说明。

表头位置、层级、派生列名、非交易行数量、日期范围、收支合计和文字非空率都通过这些检查行展开，不在报告中另建重复结构。

## 九、兼容与失败边界

- 旧的一行表头调用继续可用；
- `find_header_row` 保留为兼容入口，但内部改用新的结构识别；
- 默认表头行数为一行，新增参数均提供默认值；
- 不改变匹配器输入字段、候选生成、可信度、重要性或分流；
- 不改变原有报告工作表名称和业务口径，只增加一个工作表；
- 读取或预检查失败时不创建半成品报告；
- 用户取消普通提示时不视为程序错误。

## 十、测试设计

先写失败测试，再做最小实现：

1. 一行表头、标题行、多行表头、合并表头和稳定去重列名；
2. 结构候选接近时披露歧义；
3. 文件不可读、空数据、必填列缺失、日期全失败、金额全失败和方向无效；
4. 日期范围差异、收支合计差额、少量解析失败、非交易行和低非空率为提示；
5. 银行与日记账方向口径及收支合计可复算；
6. 无界面入口在阻止事项前不创建匹配器；
7. 普通提示回调的继续与返回两条路径；
8. 最终 Excel 含“输入预检查”且内容与运行一致；
9. 现有全量测试、语法检查、中文编码检查、差异检查和最小 GUI 导入/启动检查。

## 十一、领域语言与决策记录

本次会在 `CONTEXT.md` 增加“输入预检查”“阻止事项”“普通提示”三个业务术语，避免与正式匹配结果或未达账项混淆。

本方案不新增 ADR。选择自包含模块属于局部、可逆的实现边界，未同时满足“难以逆转、脱离背景会令人意外、存在长期锁定权衡”三个条件。

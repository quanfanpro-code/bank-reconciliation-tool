# 余额断档局部降级设计（2026-09-06）

对应需求：`docs/requirements/2026-09-06-余额断档局部降级-requirement.md`

## 方案比较

- **方案 A（推荐）：断档窗口局部降级**。连续性异常在产生时就带上窗口（两个余额锚点之间的日期区间），总体控制把"可定位且覆盖不过半"的断档从整体降级理由中剔除，降级戳只盖在任一侧记录落入窗口的候选上。报告结论改为披露断档位置与受影响区间。
- 方案 B：取消余额降级、只披露不降级。改动最小，但断档窗口内的记录可能受缺行影响，直接自动确认放弃审计谨慎性；用户已在需求阶段否决。
- 方案 C：只在报告层改措辞，机制不动。用措辞掩盖实质问题，否决。

方案 A 实现成本中等（四处代码＋测试），可逆（revert 即回退），与现有"按戳降级"管道完全兼容。

## 数据流

1. `balance.py check_balance_continuity`：每条连续性异常增加 `窗口起`、`窗口止` 两个键。
   - 日界断档：窗口起＝上一个建立收盘锚点的交易日，窗口止＝断档日。循环内新增 `previous_anchor_day` 跟踪。
   - 日内无法闭合（贪心重放失败）：窗口起＝窗口止＝当日。
2. `balance.py build_overall_controls`：
   - 从两侧连续性异常收集窗口，写入 `OverallControlResult.affected_windows`。
   - 局部化条件：存在连续性异常、每条都带可解析窗口、窗口覆盖的有记录交易日数 ≤ 全部有记录交易日的一半。
   - 满足时：`存在N处余额连续性异常` 和 `期初加净发生额与期末余额相差X` 两条原因保留在 `reasons` 供披露，但不再计入 `structural`；`scope_limited` 只由其余结构性原因（期间无法计算、口径未验证、解析异常等）决定。
   - 不满足时维持现状整体降级。
3. `data_structures.py OverallControlResult` 新增 `affected_windows: tuple[tuple[pd.Timestamp, pd.Timestamp], ...] = ()`。
4. `matcher.py` 盖戳处（现 1621 行）：
   - `overall_scope_limited` 为真 → 全部候选盖戳（不变）。
   - 否则 `affected_windows` 非空 → 仅当候选任一侧记录日期落入任一窗口才盖戳；`overall_control_reasons` 写该窗口的断档日期与差额，例如"余额连续性在2025-07-01断档（差额499,558.37），仅该断档窗口内关系降级"。
5. `matching_policy.py` 不变：仍按 `overall_scope_limited` 证据戳降级。
6. `reporter.py` 系统结论：`scope_limited` 时维持现状；仅局部窗口时改为"已完成自动分析；余额在X、Y断档，仅断档窗口内关系降为疑点，其余关系按证据正常确认"。范围说明依赖 `overall_limited`，局部化后自动不再列"总体余额控制"。
7. `input_precheck.py` 输入检查"总体余额控制"项：存在可定位断档时解释改为"……仅断档窗口内候选不得无保留自动确认"。

## 错误处理

- 异常缺少窗口键或日期不可解析 → 该异常不参与局部化；只要有任何一条不可定位即回退整体降级。
- 相邻断档产生相邻窗口：不合并，各自独立判断（简单且不影响正确性）。
- 无余额列、余额全不可解析：维持现状（未实施/整体降级），不由本次改动处理。

## 测试策略

新增 `tests/test_余额断档局部降级.py`：

1. 窗口外零差额匹配自动确认、窗口内匹配降为疑点（三日构造样本，中间日断档）。
2. 断档无法定位（异常无窗口）→ 回退整体降级。
3. 窗口覆盖过半 → 回退整体降级。
4. 跨窗口匹配（一侧在窗口内、一侧在窗口外）→ 降级。
5. 系统结论文案包含断档日期、不含"全部降为疑点"。

同步更新断言整体降级的既有测试预期（test_第二阶段终审范围与规模、test_阶段一终审余额解析范围等，以实际失败为准逐一核对）。

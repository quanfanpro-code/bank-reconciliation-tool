# 单账户业务匹配方案

日期：2026年9月5日。需求已由用户回复“ok”确认；用户随后授权“后续你自主决策自己执行，不要问我了”，本方案及后续计划由开发自主决策并留存依据。

## 目标

在一个账户的银行流水与银行存款序时账之间，可靠处理双向拆并、多对多、工资整批。保留原文件、Windows入口、既有输入格式及自动输出方式。

## 方案比较

| 方案 | 业务效果 | 实现与维护 | 风险、验证和可逆性 |
| --- | --- | --- | --- |
| 只改分数、提高组合上限 | 可缓解个别排序问题，不能识别35笔不等额工资完整批次 | 改动少，但仍靠金额枚举 | 容易增加凑数候选及耗时，不能满足全部已确认需求 |
| 在现有流程补充业务分组与共同证据判断（采用） | 先找到有依据的完整组，再统一处理确定关系、多解和差异 | 复用候选结构、精度、分流和报告，少量局部代码及一个按需分离的分组模块 | 需要防止误分组和过度排除；用正反例及端到端测试验证；可按文件恢复 |
| 重建全局求解器或由模型裁决全部交易 | 潜在搜索更广，但仍不能补出原资料缺失的依据 | 改动、依赖、维护和迁移成本高 | 全局结果难解释，验证面大，不适合本轮已明确的局部升级 |

本方案不引入新依赖、数据库、规则平台或必填业务编号。不建立多账户任务或新的人工确认流程。

## 数据流

原两表读取及映射 → 保留原始业务文字和编号 → 生成既有逐笔/组合候选及业务完整组 → 判断业务依据与冲突 → 在合理候选间识别竞争和完整闭合组 → 统一选择 → 依同一依据确定结果层次 → 输出Excel组成和原因。

组合金额继续采用原有整数精度。收入、支出分别计算；本轮不增加混合正负净额结算。

## 业务组怎样形成

1. 从已经选入匹配的辅助字段和原摘要中识别明确的业务号、批次号等依据。仅在明确字段或标记上下文中提取，不把任意长数字、账号、日期、凭证号自动当成共同业务号。辅助字段另存原值及原始类型；只有数值类型且为整数的编号才去掉读取时产生的“.0”，文本编号、前导零和分隔符保持不变。
2. 按来源一侧收集完整成员，以日期范围、收付方向、业务编号、原始摘要及可比较的对方信息限制组范围。已有编号不同的记录，不允许经更宽的摘要规则重新混到同一组。普通同方信息加“收款”“付款”“货款”“报销”等宽泛摘要不能单独定义批次边界。
3. 账内凭证组保留年度、期间和凭证字等已有上下文；凭证号仅支持账内归集，不能直接当作银行端编号。完整凭证只证明日记账侧组成完整，不能单独证明银行侧对应关系。在允许日期窗内且双方金额完整一致时，双方明确同一对方可以作为跨双方证据；只有相同具体摘要，且没有共同业务编号、交易流水号或明确对方时，保留候选但结果仍为疑点。若金额超出普通金额窗，仍须共同业务编号，或“明确对方＋具体摘要”等更强证据。
4. 不等额工资按已有批次依据或同日明确工资用途的完整记录组归集，允许员工姓名不同和记录不相邻。明确批次号、工资或双方同类批量用途已经证明一侧为汇总、另一侧为明细时，平台或汇总单位与员工、供应商、客户明细主体不同只形成层级核查提示；1对1、普通货款和没有批量边界的主体冲突仍阻断自动确认。不同发薪期间、不同明示批次不能合并。缺少足够区分依据的竞争批次保留歧义。
5. 直接计算上述完整组的收支，产生1对多、多对1或多对多候选，不让完整批次受通用子集搜索30笔限制。通用搜索仍用于没有完整组依据的剩余可能关系；通用组合搜索和完整凭证的跨侧候选池都采用有界检查，触发上限时保留候选总量、实际检查或保留范围及未穷尽状态。
6. 普通无依据的同日/月总额候选保留可解释的组级用途，但不能无条件优先，更不能覆盖明确业务冲突或更强的对应。

员工明细与工资汇总的比较，以批次和业务范围为主；多名员工不是一个拼接后的“交易对手”。只有已证明为同类批量业务且双方记录层级确实不同，才把主体集合差异改列为核查提示；普通逐笔或没有批量边界时，双方实际主体明确不同仍保留冲突。

## 选择和歧义

业务依据、排序和结果分流使用同一套判断，避免在三个环节采用互相矛盾的规则。

- 明确冲突候选不能污染正确关系的多解判断；排除的是这条关系的合理性，原记录仍完整保留。
- 同等业务依据下，完整且收入、支出均无差额的关系优先于部分组成造成的差额。
- 共同业务P01的1,000与990有10元差异，不能被无共同信息的另一笔1,000挤掉；零差不是无条件最高优先级。
- 两个同层次、都无法排除的关系仍是多解，不能用1分差距证明唯一。
- 闭合组仍要检查范围和业务冲突，不能仅因“整组”或“完整凭证”标记就自动确认；日期窗内、金额完整一致且双方明确同一对方时已有跨双方证据，只有相同具体摘要而缺少编号、流水号和明确对方时仍列疑点，金额超出普通金额窗时须共同业务编号或“明确对方＋具体摘要”等更强证据。
- 已确认关系之间原行不重复占用；疑点候选的竞争组成在报告中能查清。
- 账户、币种、金额口径缺失或未验证，以及期间、数据人口、总体余额控制或余额解析异常使总体范围受限，受影响关系统一降为疑点、范围未知。

不引入新业务状态，沿用自动确认、整组勾稽一致、自动归集事项、疑点事项和未找到候选。重要性水平继续只用于分级，不证明关系。

## 输入和报告

沿用辅助文字勾选界面，增加对明确业务编号、批次编号列的自动建议；用户现有选择仍有效。编号文本保留前导零。账户、卡号和账内凭证号不因此变成默认发送给在线模型的字段。在线模型仍只能比较原候选，不能解除明确冲突。

核心为报告提供MatchCandidate.evidence中的：
- business_basis：可直接展示的业务分组/对应依据字符串；
- alternative_candidate_ids：仍成立的竞争候选编号序列；
- alternative_candidate_count：竞争候选的精确总数；
- alternative_candidates_truncated：竞争候选是否只列示样本；
- 其他内部证据由核心维护，不暴露成新用户流程。

报告增加业务依据和竞争组成说明，保留完整原行。竞争候选报告精确总数，最多列示10个按业务内容稳定选出的关系号样本；换行序不改变样本。组级勾稽率只计入已确认的组合或整组一致，不把零差疑点算成已勾稽。分别写清银行侧和账侧覆盖笔数、金额与统计口径；“自动完成”不等于匹配率。

## 错误处理与性能

缺少编号不停止运行；退回原有日期、文字和组合能力。无法完整证明的组按疑点或单边记录输出。数据量与搜索上限由开发实测决定，不再向用户询问。完整组先求和；完整凭证按共同编号、交易流水号和对方建立索引，并在需要更强证据时组合具体摘要，缩小跨侧候选池。通用组合搜索和完整凭证候选池均设置上限，记录候选总量、实际检查或保留范围及是否未穷尽，持续检查取消标记，不引入无界枚举。

生产入口沿用现有日志与百分比回调。匹配器的十个候选阶段分别输出完成状态、新增候选、累计候选和耗时；智能组合的串行与并行分支输出已处理来源任务数；候选去重选择输出双方覆盖行数。报告器分别输出表格构造、Excel初次写入和排版保存。匹配器0%—100%线性映射到整项任务30%—75%，文件读取、输入检查、报告生成分别占用其余区间。真实数据验收用带 `append()` 方法的实时证据列表同时留存原始回调和即时输出，并每15秒输出一次当前阶段心跳。

# Agent 低分不改选修复方案

日期：2026-11-24
需求依据：`docs/requirements/2026-11-24-Agent低分不改选-requirement.md`
修复起点：`e359e43414e1762378078be7edb1f073755fe426`

## 方案比较

| 方案 | 做法 | 成本与风险 | 可逆性 |
| --- | --- | --- | --- |
| 副本试算，确认后落地（推荐） | 在现有 Agent 答复处理处复制所选候选，只对副本评分和检查；通过确认条件才锁定副本，未通过则原候选不变 | 改动最小，直接满足“证据不足不改”；不碰评分公式、重要性分流和搜索流程 | 高，撤销这一处即可 |
| 先改原候选，失败再恢复 | 按现状先写入低分，未通过确认时恢复原分数 | 后续歧义刷新可能再次读取低分，容易遗漏恢复路径，状态管理更复杂 | 中 |
| 调整评分或排序公式 | 改低分权重或候选排序规则 | 会影响所有本地和 Agent 候选，超出本次范围，回归风险最高 | 低 |

推荐第一种。复用现有 `dataclasses.replace` 和 `_agent_verified_candidate`，不增加依赖或新模块。

## 数据流

1. 继续按现有逻辑校验 Agent 答复编号、分数和理由，并写入复核记录与次数。
2. 对 Agent 所选候选建立副本，在副本上写入答复并重新评分。
3. 副本继续通过现有 `_agent_verified_candidate` 检查金额、方向、日期、冲突、其他合理候选和候选可区分性。
4. 达到确认条件时，沿用现有 `_lock` 锁定经确认的副本，高分确认及交易明细依据保持不变。
5. 未达到确认条件时，不把副本的分数或答复写回原候选。原候选的评分、选择、原始行归属和后续重要性分流均与没有这次答复时一致。
6. 空答复、无效答复和超时沿用现有降级及统计，不进入确认。

## 错误处理与边界

- 低分：不改变原候选，不自动确认；重要性水平仍按原规则决定留存、抽查或逐项核查。
- 明确冲突：即使高分也不确认，原候选不被本次试算改变。
- 候选无法区分或未完整展示：继续保留疑点，不确认。
- 高分且所有检查通过：正常确认，不让本次修复削弱已验证能力。

## 测试策略

在现有 `tests/test_Agent与核对闭环.py` 参数化场景中，把“最终仍选择1月天然气款”的断言同时用于100分和20分：

- 修改前：20分场景会改选12月，断言应失败，形成有效 RED。
- 修改后：20分仍选择1月并保留原有高风险核查，100分仍自动确认并写入依据，形成 GREEN。
- 同文件继续运行明确冲突、候选无法区分、未完整展示、超时及报告统计测试。
- 随后运行受影响的银行入口、余额配对和报告回归；按本次改动范围决定是否需要全量测试。

测试仍核对实际最终记录和五表结果，不只检查答复编号或内部函数调用。

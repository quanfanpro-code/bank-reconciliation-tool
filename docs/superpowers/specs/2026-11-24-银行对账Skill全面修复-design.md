# 银行对账技能全面修复设计

## 方案比较

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| 优先采用 | Agent 驱动读表和核对，结合程序读出的工作表、表头、原行和已有识别建议，确定格式与业务字段。现有程序验证字段、计算和出表。 | 常见格式可复用已有识别结果。格式变化时，Agent 有原表和两侧证据可用，22 个反例可以在同一流程验收。 |
| 每账户全部重新识别版式 | 每户都由 Agent 从头判断工作表、列与金额口径，再交给现有程序复算。 | 能读业务文字，重复版式也要重新判断，批量效率较低。 |

## 每份文件的读取结果

先检查同一 Excel 文件内各工作表。原表的本方账号、列内容、日期和交易形态用于辨认交易页和续页。表内明确的查询期间和零发生额同样是读取结果。每笔交易都能定位至原工作表和原行。

读表阶段就由当前 Agent 查看两份原表的页签、表头和有代表性的原行。程序给出常用列建议及需要核实的内容。Agent 根据两表和上下文确定原列含义，包括可用于配对的对方账号、订单编号和说明列。通过现有列映射参数或复核交接将工作表、原列名、业务用途和原行依据交给程序，程序用列值、收支总额和余额验证。已核定的同结构格式可复用。读表阶段的反馈在匹配前交给当前 Agent 自行处理。账号按本方和交易对方分别保存。金额保留币种、原始收付和用于余额计算的净变动。识别时试算和正式读入使用相同口径。

批量用核实后的本方身份配户。两份同侧文件疑似重复时先比较表内身份、期间和实际内容，复用读表结果确定范围。对未成对的账户，输出已经读取的一侧和核对范围，继续处理其他账户。金额格解析失败时先复读原值、检查列口径和公式值，再用同笔业务依据及余额变动验证可还原的金额。只对原值确实缺失的部分写明实际原行和影响。

## 每笔交易的核对

不同匹配规则共用日期、币种、账号、交易编号及已经核实的用途事实。原付款与退款的关联以原交易或业务编号为先。月合计相等独立于逐笔或合笔确认。余额只在能够验证的区间用于支持交易匹配。

沿用已有组合搜索和原文比对。达到上限时先用金额和已有业务线索缩小搜索，再补查仍可能的组合。程序给 Agent 看每组涉及的原行、金额、实际日期、摘要、附言、对方和编号。Agent 将文字的业务含义与日期一起核对。例如三笔都是 15 万元，银行附言写 1 月天然气款，只有一笔日记账摘要也指向 1 月。同日的其他月份款项仍应排除。程序验证 Agent 引用的原文、金额及日期，并按原行保留已核实的业务冲突。请求未在时限内返回或答复无效时，将互相争用同一原行的记录重新整理后重试一次，已核实的证据继续有效，本地比较照常执行。

同一组原行在两侧收支分别对平时，可以确认整组。出现争用原行时，复用现有整体选配函数。先排除明确违反收支方向、币种、账号、业务事实或日期容差的关系，再比较原文依据、日期和金额的吻合程度以及对其余原行的影响。经完整比较仍等效的关系按交易内容稳定排序，内容完全相同时用真实原出处落定。最终 Excel 写采用的一套关系及实际剩余差额，每条原行只占用一次。

## 结果落到原 Excel

总览写可核对的账户与范围。原日表和月表按两个方向比较收付，分别显示有证据的余额。日表在已有说明栏列出余额断差及日期。原交易明细保留原行、匹配结果、重复线索和实际解释。原待核对页显示差异及该笔能从两表确认的事实。重要性金额用于差异大小和排序。

技能入口、复核分流和出表共同使用自动核对结果。把原本要求人工全查或抽查的路径改为程序复算、Agent 读原文、最终选择或差异说明。Excel 输出校验失败时由技能检查原因，可恢复的问题修正后在本次运行重试。一个账户的失败写明文件、完成范围和具体原因。

人工仅用于重大异常最终需要的业务决定。程序必须先完成读取、交叉验证、补查及可计算的核对，把已查事实和剩下的具体决定放在现有 Excel 的说明里。常规配置、读表、配对、抽查分流、内部超时或出表重试直接由技能处理。

## 验证和交付

用需求记录的 22 个反例验证实际技能入口或在入口调用的模块。相同交易换金额列格式、表头、列顺序和工作表布局时比较同一结论。另保留格式、只改变账号、日期、币种或编号，检查错误关系被排除。正常余额链、原路退款、跨日合笔、批量配户和已读原行还要回归。

先改随技能交付的引擎和入口，仓库 README 与技能 README 都说明实际用法。原输入和既有报告只读。按入参、匹配和报表分段做验证，最后用同一版完整技能重新跑两份原表到六表输出的验收流程。

# 银行流水核对工具全面复核升级——方案设计

日期：2026-07-28  
对应需求：`docs/requirements/2026-07-28-全面复核升级-requirement.md`

## 一、设计目标

本次设计同时解决四个问题：

1. 修正已经实证的金额方向、期初余额、批量工资和多对多核销错误；
2. 把现有互不统一的“高、中、低”改成可解释的 0～100 综合可信度；
3. 使用两个重要性阈值提高自动处理率，同时保留审计痕迹；
4. 增加可选的大模型语义辅助和详细 Excel 报告，但不让大模型成为必需依赖。

设计必须保留现有数据加载、金额精度、组合求和和 Excel 输出能力，
避免无必要的整套重写和新增第三方依赖。

## 二、方案比较

### 方案 A：在现有七步匹配后增加阈值和大模型

做法：

- 保留现有每一步“找到后立即标记匹配”的方式；
- 修复已知错误；
- 在全部匹配结束后计算组金额、明显微小错报和待复核状态；
- 对现有匹配结果补充大模型评分。

优点：

- 改动文件和代码量最少；
- 上手快；
- 回滚简单。

缺点：

- 错误候选在前面步骤已经占用流水，后面的统一评分无法重新选择；
- 七个阶段继续各算各的置信度，70%门槛只是表面统一；
- 多字段文字证据和大模型无法真正参与候选竞争；
- 日/月多对多、累计差异池和详细报告会继续散落在多个位置；
- 容易出现“修完一个入口，另一个入口仍然错”的同类问题。

结论：不采用。它适合作为临时补丁，不足以支撑本轮已确认的业务规则。

### 方案 B：保留算法，新增统一候选、评分和分流中心（推荐）

做法：

- 继续使用现有精确匹配、日期容差、批量聚合、组合求和和日/月汇总算法；
- 各阶段先产出候选，不立即把候选当作已确认匹配；
- 所有候选进入同一套证据评分、冲突检查、候选排序和状态分流；
- 大模型只增强文字证据；
- 重要性水平、明显微小错报和月度差异池在统一分流中心处理；
- 报告直接读取统一候选证据，不再从零散字段反推理由。

优点：

- 现有成熟算法可以复用；
- 可信度和自动/人工状态真正统一；
- 每个结论都有结构化依据，便于生成详细报告；
- 可单独测试候选生成、评分、分流、大模型和报表；
- 将来调整权重或增加证据列时，不必重写每个匹配阶段。

缺点：

- 需要调整 `matcher.py` 的候选提交方式；
- 报告和数据结构需要同步升级；
- 比方案 A 的回归范围大。

结论：推荐。它是在正确性、自动处理率、维护成本和可逆性之间最平衡的方案。

### 方案 C：建立全局关系图并求全局最优解

做法：

- 把所有一对一、一对多、多对一和多对多候选建立成全局关系图；
- 使用整数规划或专用优化器选择总评分最高的无冲突组合。

优点：

- 理论上可以得到全局最优组合；
- 对大量相同金额、相似文字的复杂数据更有优势。

缺点：

- 多对多候选数量可能爆炸；
- 通常需要引入新的优化依赖；
- 求解过程难以向财务用户解释；
- 性能和稳定性风险高；
- 回滚和维护成本最高。

结论：不采用。只有真实数据证明统一候选的确定性选择明显不足时，才考虑该方案。

## 三、推荐架构

### 3.1 总体数据流

```text
读取文件
  → 列映射与金额方向标准化
  → 多个辅助文字字段标准化
  → 分阶段生成候选
  → 本地证据评分
  → 可选的大模型语义评分
  → 统一候选排序与冲突消解
  → 重要性水平和明显微小错报分流
  → 自然月差异池累计
  → 自动确认 / 待人工复核 / 未找到候选
  → 详细 Excel 报告
```

### 3.2 模块边界

#### `data_structures.py`

保留 `MatcherConfig` 和现有结果结构，新增最少的领域数据结构：

- 匹配候选；
- 分项评分；
- 大模型判断记录；
- 最终处理状态；
- 差异池归属。

现有 `matches` 对外字段继续保留，新增字段只做向后兼容扩展。

#### `data_loader.py`

负责：

- 修复银行与日记账的方向差异；
- 让单列方向、借贷分列和含正负号模式使用同一套来源感知规则；
- 保存用户选择的多个辅助文字字段；
- 记录所有日期、金额和方向解析失败；
- 不在此处进行候选评分。

#### `matcher.py`

负责：

- 生成一对一、一对多、多对一和多对多候选；
- 复用现有 DFS、折半枚举、贪心和索引能力；
- 计算金额、日期、文字和结构证据；
- 统一排序候选并解决同一流水被多个候选占用的问题；
- 不负责 Excel 展示。

#### 新增 `llm_assistant.py`

负责：

- OpenAI 兼容接口；
- 模型列表与连接测试；
- 在线与本地数据最少化；
- 固定结构请求和返回校验；
- 超时、有限重试和自动降级；
- 运行期内存缓存；
- 清理报告中的敏感信息。

仅使用 Python 标准库完成 HTTP 和 JSON 处理，不新增必需依赖。

#### `reporter.py`

负责：

- 根据结构化候选证据生成汇总、组成明细、明显微小错报、待复核和大模型明细；
- 保留数值类型；
- 生成复核结论下拉框；
- 不重新计算匹配业务逻辑。

#### `gui.py`

负责：

- 收集并校验两个重要性阈值、最低可信度、多文字列和大模型设置；
- 保存本次运行期间的大模型密钥；
- 提供连接测试；
- 以清晰的卡片和独立配置窗口保持主界面整洁。

## 四、金额和方向设计

### 4.1 来源感知方向

银行流水：

- 贷、收入、收、入账、转入、存入、CR → 正数；
- 借、支出、付、出账、转出、取出、DR → 负数。

日记账：

- 借、收入、收、入账 → 正数；
- 贷、支出、付、出账 → 负数。

无法识别的方向返回解析失败，不使用默认正数。

### 4.2 匹配组金额

分别计算：

- 银行侧绝对金额合计；
- 日记账侧绝对金额合计。

两者取较大值作为匹配组金额。
这样不会把同一业务在两边重复计算，也不会被组内正负抵销掩盖。

### 4.3 收入与支出分别比较

每个候选分别计算：

- 银行收入合计与日记账收入合计的差异；
- 银行支出绝对值合计与日记账支出绝对值合计的差异。

候选总差异为两项绝对差异之和。
即使用户勾选“允许异号”，收入和支出也不能互相抵销。

## 五、候选生成

### 5.1 一对一候选

候选来源：

1. 日期和金额完全相同；
2. 金额相同、日期在容差内；
3. 金额差异不超过明显微小错报临界值、日期和文字存在合理关联；
4. 白名单关键词命中。

当同一金额有多个候选时，不再只取最近日期后才检查摘要，
而是对所有候选同时计算日期和多字段文字证据。

### 5.2 一对多和多对一

复用现有组合求和算法，但改为：

- 精确和优先；
- 允许在明显微小错报临界值内寻找最小差异组合；
- 同时考虑源记录日期与全部目标记录日期；
- 候选数量超过上限时，按日期、文字和金额接近程度共同筛选，
  不再只按绝对金额大小截断；
- 返回候选，不立即占用流水。

### 5.3 批量工资

必须同时满足：

- 当前日期组本身达到最小笔数；
- 银行组和日记账候选金额关系成立；
- 双方非空文字字段满足工资、代发、薪酬等业务条件；
- 日期范围符合规则。

“全月同金额记录超过 10 笔”不能替代“当前日期组达到 10 笔”。

### 5.4 多对多

按以下顺序产生：

1. 同日收入组、支出组；
2. 同一自然月内，经过前序匹配后剩余的收入组、支出组；
3. 用户允许异号时，仍分别核对收入与支出结构。

日/月多对多不再要求双方正负笔数完全相同。
笔数差只作为结构评分因素，不作为变相的绝对否决条件。

同月多对多可以自动确认；跨月多对多只能进入待人工复核。

### 5.5 候选最小成立条件

明显微小错报规则不能凭空制造候选。候选至少需要：

- 日期范围成立；
- 收支方向可解释；
- 双方均有真实流水；
- 金额差异在允许范围内；
- 不存在明确冲突的唯一编号或对方信息。

## 六、统一综合可信度

### 6.1 分项权重

基础综合可信度为 0～100：

| 分项 | 最高分 | 含义 |
|---|---:|---|
| 金额关系 | 40 | 收入和支出分别比较；完全相等最高 |
| 日期关系 | 15 | 同日最高，随日期距离下降 |
| 多字段文字证据 | 30 | 摘要、业务说明、用途、对方户名等 |
| 结构与唯一性 | 15 | 候选唯一性、组合复杂度、规则命中、冲突证据 |

### 6.2 大模型对评分的影响

大模型不另加一个可能把总分推过 100 的奖励项，而是增强“多字段文字证据”：

- 未调用大模型：使用本地文字评分；
- 调用成功：文字评分由本地评分与模型语义评分共同形成；
- 推荐初始比例：本地 40%，模型 60%；
- 调用失败：完整退回本地文字评分。

大模型最多影响 30 分的文字部分，不能覆盖金额、方向、日期和重要性规则。

### 6.3 硬性限制

- 方向无法识别：不生成候选；
- 收入/支出结构存在重大冲突：不自动确认；
- 多个同等候选且没有任何文字证据：综合可信度最高 69；
- 跨月多对多：无论分数多少都待人工复核；
- 匹配组金额超过实际执行重要性水平：无论分数多少都待人工复核；
- 大模型返回候选集以外编号：忽略该回答并降级。

### 6.4 确定性候选选择

候选排序依次使用：

1. 硬性规则是否通过；
2. 综合可信度从高到低；
3. 金额差异从小到大；
4. 日期跨度从小到大；
5. 组合笔数从少到多；
6. 原始文件行号。

按该顺序选择互不占用同一流水的候选。
相同数据和相同参数必须得到相同业务结果。

## 七、状态分流

对已选择候选按以下顺序处理：

1. 匹配组金额超过实际执行重要性水平 → 待人工复核；
2. 跨月多对多 → 待人工复核；
3. 匹配组金额未超限，且差异不超过明显微小错报临界值：
   - 差异为 0 → 自动确认；
   - 差异非 0 → 明显微小错报自动处理；
4. 其他候选综合可信度达到最低门槛 → 自动确认；
5. 其他候选 → 待人工复核；
6. 没有候选 → 未找到候选。

### 7.1 月度差异池

明显微小错报按自然月、来源和收支方向进入四个差异池。

如果一个候选同时存在收入差异和支出差异，分别进入对应差异池，不得抵销。

某个月、某个池累计绝对差异超过实际执行重要性水平时：

- 该池组成项目不再作为独立自动处理结果；
- 汇总成一项待人工复核事项；
- 报告附全部组成明细；
- 用户只需复核整池结论。

## 八、多字段文字证据

### 8.1 列选择

银行与日记账分别保存多个辅助文字列。
默认自动选择摘要、业务说明、交易用途、对方户名、附言和备注。

账号、卡号和凭证号默认不选。
账号如果由用户选择，只在本机形成“相同/不同”信号，在线模式不发送原值。

### 8.2 本地比较

本地文字评分包括：

- 清除空白、全半角和常见噪声后的字面相似度；
- 关键词和核心名称重合；
- 字段完全一致；
- 明确冲突；
- 多字段中最佳对应关系。

不得把多个字段无标签地简单拼成一长串。
报告保留字段名、原值摘要和各字段得分。

## 九、大模型辅助

### 9.1 调用范围

默认只调用真正含糊的候选：

- 同一流水存在多个合理候选；
- 本地综合可信度接近自动确认门槛；
- 文字表达差异大但金额和日期合理；
- 待人工复核组需要模型帮助排序候选。

唯一且证据充分的精确匹配、明显不成立的候选不调用大模型。

### 9.2 接口协议

提供三种协议选择：

- 自动；
- Responses；
- Chat Completions。

默认基础地址：

- 在线 OpenAI 兼容服务由用户填写；
- LM Studio：`http://localhost:1234/v1`。

支持：

- `GET /v1/models` 获取模型列表；
- `POST /v1/responses`；
- `POST /v1/chat/completions`。

“自动”模式先使用 Responses，服务明确不支持时退回 Chat Completions。

### 9.3 固定返回结构

请求要求返回固定 JSON：

- `selected_candidate_id`；
- `semantic_score`；
- `reason`；
- `supporting_evidence`；
- `conflicting_evidence`；
- `uncertainty`；
- `suggested_status`。

程序逐字段验证类型、范围和候选编号。
结构化输出不受支持时，允许一次普通 JSON 重试；仍失败则降级。

### 9.4 稳定性

- 非流式调用；
- 温度默认为 0（服务支持时）；
- 每组最多一次正常调用和一次格式修复重试；
- 每次调用有独立超时；
- 本次运行内按脱敏后的候选内容缓存，避免重复计费；
- 停止任务后不再发起新调用；
- 不把接口密钥写入任何持久文件。

### 9.5 数据最少化

在线模式只发送当前候选组必要字段。
文件路径、完整账号、卡号、整份流水和未勾选字段不进入请求。

本地 LM Studio 可使用用户勾选的全部辅助字段。

报告中的接口地址去除查询参数和认证信息；
模型原始回答在清理敏感信息后保留。

## 十、报告设计

### 10.1 Sheet 结构

保留现有核心 Sheet，并增加结构化明细：

1. 核对汇总；
2. 每日统计；
3. 月度统计；
4. 匹配明细——每个匹配组一行；
5. 匹配组成明细——每笔原始记录一行，不伪造一一对应；
6. 明显微小错报；
7. 待人工复核；
8. 银行未达；
9. 日记账未达；
10. 余额差异明细；
11. 余额连续性异常；
12. 大模型辅助明细；
13. 运行参数；
14. 解析异常明细。

没有数据的可选 Sheet 自动省略，但“运行参数”和关键异常信息不能因业务数据为空而丢失。

### 10.2 匹配组展示

“匹配明细”每组一行，至少显示：

- 组编号、最终状态、匹配阶段；
- 银行笔数、日记账笔数；
- 双方收入、支出和净额；
- 组金额、收入差异、支出差异、总差异；
- 日期范围；
- 综合可信度和四项分数；
- 自动/待复核原因；
- 差异池信息；
- 是否使用大模型。

“匹配组成明细”逐笔显示原始文件行号、来源、日期、金额和辅助文字字段。

### 10.3 待人工复核

每个待复核组或超限差异池一行。
“复核结论”使用 Excel 下拉选项：

- 接受；
- 拒绝；
- 暂不处理。

默认“暂不处理”，旁边提供“复核说明”空白列。

### 10.4 大模型明细

记录请求编号、模型、脱敏接口、候选、发送字段、本地评分、模型判断、
支持证据、冲突证据、不确定性、最终分流、耗时、用量、错误和脱敏原始回答。

### 10.5 数值与统计

- 金额、分数、累计值、笔数和比率保持 Excel 数值类型；
- 精确匹配率与自动处理率分开；
- 低置信度按匹配组统计，不再用银行行数除以匹配组数；
- 任何占比不得超过 100%；
- 匹配组、组成明细和未达账项使用稳定排序。

## 十一、GUI 设计

### 11.1 主窗口

遵循 `desktop-gui-style` 的卡片化、高信息密度和日志优先原则：

1. 页眉卡片：标题、短说明、主题切换；
2. 输入文件卡片：银行流水、日记账、表头检测；
3. 核对策略卡片：
   - 实际执行重要性水平，默认 100,000 元；
   - 明显微小错报临界值，默认 5,000 元；
   - 自动确认最低综合可信度，默认 70%；
4. 匹配设置卡片：
   - 当前列映射摘要；
   - “配置列映射与辅助字段”按钮；
   - “高级匹配参数”按钮；
5. 大模型辅助卡片：
   - 启用开关；
   - 当前模式、接口和模型摘要；

## 十二、错误处理

### 12.1 数据错误

- 文件不存在、格式不支持、列映射缺失：开始前阻止运行；
- 日期、金额和方向解析失败：记录原始行号和原因；
- 大量解析失败：停止并给出可理解的列映射提示；
- 全部数据为空或被过滤：仍生成运行参数和解析异常报告。

### 12.2 匹配错误

- 单个候选计算失败：记录阶段、候选和原因，继续其他候选；
- 算法超时或内存阈值触发：停止该候选并使用有限兜底；
- 不能把异常静默当作“无候选”。

### 12.3 大模型错误

- 连接、认证、限流、超时、模型不存在、返回格式错误分别记录；
- 密钥从错误文本中清除；
- 大模型失败不影响基础核对；
- 报告显示受影响的候选组和实际降级方式。

### 12.4 报告错误

- 输出目录不可写时给出明确提示；
- Sheet 名和单元格内容清理 Excel 非法字符；
- 用户原始文字不得被当作 Excel 公式执行；
- 保存失败不得覆盖原始输入文件。

## 十六、推荐结论

采用方案 B：保留现有算法能力，新增统一候选、评分和分流中心。

该方案能在不引入全局优化器和新必需依赖的前提下：

- 修复根因而不是继续堆补丁；
- 提高“一坨做账”的自动处理率；

- 生成足够详细、可追溯、可在 Excel 中直接复核的结果；
- 保持 GUI 整洁并为将来扩展留下清晰边界。
